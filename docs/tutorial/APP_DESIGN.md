## 1. 一条流水线，不是几种模式

最早的想法是「SLAM 模式 / 测距模式」×「已有地图 / 未知地图」的 2×2。
**它塌缩了**——两个轴是正交的，而且都不是"模式"：

| 轴 | 是什么 | 什么时候变 |
|---|---|---|
| **地图从哪来** | 载入 / 新建 | **启动那一刻定一次** |
| **你要干什么** | 看轨迹 / 量尺寸 | 随时切，**而且经常同时需要** |

四个格子里的**流水线是同一个**：

```
载入 / 新建地图 → 惯性初始化 → 定位（始终在跑）→ 快照出口
                                                     │
                          ┌──────────────────────────┤
                          ▼                          ▼
                     2D 地图视图                 预览 / 测量视图
```

**为什么不做成模式**：模式意味着互斥的状态机，而这几个轴不互斥。
做成模式会立刻遇到「我想边看轨迹边量」这种需求，然后靠特例硬塞。

## 2. 入口、两个按钮，与「图」的三种来源

### 2.1 入口页只记选择

```
打开 App
   ↓
入口页：  [ ＋ 新建地图 ]
          ┌──────────────────────┐
          │ <名字>     09-27 18:20 │   ← 已保存的图（列表，空时显示提示）
          │ <名字>     09-26 11:03 │
          └──────────────────────┘
          [ 录制模式 ]                ← 另一条轴，不碰地图

SLAM 主界面： [ 启动 SLAM ] [ 重定位 ]  ＋ 右上角 ☰ 抽屉
录制页：      [ 开始准备 ] [ 开始录制 ]
```

> ⚠️ **2026-09-27 改**：原先是「新建地图 / 继续上次」二选一。改成**「选一个已保存的图」**
> （列表 + 新建），并且**录制独立成一个模式**（理由见 §6 和 §7.1）。
>
> **「新建」= `loadFromFile` 传 null。** 它和「选一张旧图」是**同一个参数的两个取值**，
> 不是两种模式 —— 这正是 §2.4「一个动作、三种来源」那条的直接后果。

**入口页可以瞬间返回、改主意** —— 它不加载词袋、不读 atlas、不开相机。
三个入口都**不 `finish()` 掉入口页**，所以按 Back 能回来重选。

**列表里只能显示文件层面的东西**（名字、时间）。「这张图有多少关键帧」显示不了 ——
那要新增 JNI 查询接口，而 §6「接口约定」里没有。

**耗电因此落在明确的按钮上**，符合 09-21 那条原则（「接受不了无用资源一直耗电」）。
**不做「打开 App 就一直跑」。**

### 2.2 两个按钮，加一个抽屉

| 位置 | 什么 | 做什么 |
|---|---|---|
| 底部 | **准备 SLAM → 启动 SLAM → 结束** | 见下面那张三段表 |
| 右上 ☰ | **抽屉** | **「录制落盘」** + **「实时测距」**两个开关（**都默认关**，§6.1）+ 一条 M8 的占位 |

> **2026-10-17：底部的「重定位」按钮已删除。** 功能试过（②a，见
> `docs/changes/2026-10-17-relocalization-a.md`），单帧变换的精度不够做合并，
> 代码存档在分支 `feat/relocalization`。下面 §2.4 保留为设计记录。

**主按钮是三段**（2026-09-28 改，和录制页的两段式对齐）：

| 阶段 | 按钮 | 做什么 |
|---|---|---|
| 未准备 | `准备 SLAM` | 构造 `System` —— **贵且慢的那一步**（词袋实测 37.7 s） |
| 加载中 | `加载中…`（灰） | 没得取消：`System` 构造没法中断 |
| 就绪 | `启动 SLAM` | 开相机 + IMU + 开始吃帧 |
| 运行中 | `结束`（红） | 关相机 + IMU，停止吃帧。**`System` 保留** → 回到「就绪」 |

**为什么把「准备」和「启动」拆开**：和录制页那条同一个道理 —— **贵的那一步不该被反复付**。
「结束」之后再「启动」是**立刻**可用的（§5 决策一：`System` 跟着进程走，相机/IMU 跟着用户意图走）。

⚠️ **没有「取消准备」。** `System` 的构造没法取消，而且造好之后也没有安全的销毁时机
（它没有析构函数、`Shutdown()` 又不 join 线程 —— 见 [STAGE5](STAGE5_JNI_BRIDGE.md) §5 决策一）。
所以这个按钮是**单行道**：准备过就回不到「未准备」。这不是偷懒，是把 ORB-SLAM3 的事实
如实反映到界面上。

**抽屉里的「录制落盘」**：SLAM 跑着的时候**多挂一个落盘消费者**，
把喂给 SLAM 的同一段序列也写到 `sessions/` 里。目的见 §6.2 ——
它是 [STAGE5](STAGE5_JNI_BRIDGE.md) M5 那条「同段数据 PC 对照」的前提。
（**已实现**。录出来的 `meta.json` 里标了 `with_slam`，和「录制模式」录的分得开。）

**抽屉里的「实时测距」**（2026-10-07 加）：画面中心出现**十字 + 距离读数**，
十字附近没有地图点时给一句提示语。**关掉时连算都不算**（C++ 那边的开关，见 §8）。

**两个开关都记进 `SharedPreferences`** —— 下次进来还是上次的状态。
（这是本 App 唯一用 `SharedPreferences` 的地方。）

**词袋和 atlas 是在「启动」时加载的，不在入口页。** 原因：`LoadAtlas` 发生在
`System` 的**构造函数**里，而构造就发生在启动这一刻。
**所以第一次启动要等三十几秒**（词袋实测 37.7 s + 可选 `LoadAtlas`），界面要给进度。

**「停止」再「启动」不会重新加载** —— `System` 对象保留，只开关相机 / IMU / 喂帧。

### 2.3 「停止」= 结束会话，那张图成为「旧图」

**「停止 → 再启动」不是"继续"，是"重新接回去"** —— 靠重定位，不是自动续上。

**为什么不让它自动续上**：停止期间手机可能移动了，上一帧的位姿不再成立。
**显式按一次重定位，用户知道自己在等什么，也能挑好时机再按。**

### 2.4 「重定位」是**一个**动作，统一三件事

| 场景 | 重定位在做什么 |
|---|---|
| 入口选了「继续上次」 | 载入磁盘上的旧图，接上去 |
| 停止之后再启动 | 接回刚刚停止时那张图 |
| 走到路径点 | 在有界范围内重新定位（见 §4） |

**三者是同一个动作：把定位接到一张已存在的图上。**

**实现上就是「一个 `referenceMap` 字段」，三种来源：**

| 场景 | `referenceMap` 从哪来 |
|---|---|
| 入口选「新建地图」 | **空** —— 从零建，重定位按钮灰着 |
| 入口选「继续上次」 | **磁盘上的 `.osa`** |
| 按了「停止」 | **刚才那张当前图** |

> **粒度注意**：`LoadAtlas` 载入的是**整个 Atlas**（可能含好几张图 + 一张新建的空图），
> 而「刚才那张」是**一张 `Map`**。所以 `referenceMap` 统一成 `Map*`，
> 载入那条路要做一次「**挑关键帧最多的那张**」。

**两点要说清，否则上面两行会读成矛盾：**

- **「走到路径点」在实现上和「随便站在哪按一下」没有区别。** 路径点只是
  **给人看的标记**（§4.2）——差别在**人**身上，不在代码里。
- **重定位按钮的灰 / 亮只看 `referenceMap` 是否为空**，而它**只在「启动前且选了新建」**
  时为空。新建模式下**第一次「停止」之后它就有值了**（刚建的那张），按钮随之亮起
  —— 这是对的：走了很久想暂停，然后接回自己刚建的图。

### 2.5 「继续上次」的实际语义

**不是"加载完就完事"**：旧图在 `LoadAtlas` 时确实进内存了，
但**当前图是一张空的新图**（`System.cc:171` 的 `CreateNewMap()`）。

所以它的实际语义是：**新图照常跑，等重定位成功才切过去**（方案 A，见 §3）。

### 2.6 承接这一切的是 `SlamEngine`

上面这套状态模型由**一个新的封装类 `SlamEngine`** 持有。它在 **C++ 侧**，
是 [STAGE5](STAGE5_JNI_BRIDGE.md) 里那层 wrapper 的**完整形态**：

```cpp
class SlamEngine {
    ORB_SLAM3::System* sys_;
    ORB_SLAM3::Map*    referenceMap_;     // 可能为空
public:
    void init(vocab, settings, sensor, loadFromFile);
    void start();  void stop();           // stop 时 referenceMap_ = 当前图
    int  relocalize();                    // 0=成功，其余=失败原因（见 §4.4）
    void saveTo(path);
    Pose pose();  int trackingState();
};
```

**为什么需要一个类**：没有它，「旧图」是个散落在编排层里的概念——
得靠 `MainActivity` 记着、靠注释提醒。有了它，**三种来源收进同一个字段，
一条代码路径**。

**它最实在的价值是「切图」** —— `Atlas::SetCurrentMap()` 在 ORB-SLAM3 里
**不存在**，要自己加，而这个类**同时拥有**这个能力。

**「图」的概念完全不跨 JNI**：Kotlin 侧只看到
`nativeInit / nativeStart / nativeStop / nativeRelocalize / nativeGetPose`。
**这是个好信号** —— 说明这条边界划对了。

**⚠️ 封装要薄**：只记账 + 转发，**不试图重新定义「图」的语义**。
理由见 [MAP_FEATURE_IDEAS](MAP_FEATURE_IDEAS.md) §4 那七个被推翻的判断——
ORB-SLAM3 的 Atlas/Map 那块本身就糙（没有 `SetCurrentMap`、
`KeyFrameDatabase::serialize()` 是死代码、定位模式是作者留的 TODO）。
**薄封装至少漏的时候一眼看得见。**

## 3. 切图（方案 A）：定案

重定位成功时手上有两张图，接下来两种做法，**选 A**：

| | 做法 | 成本 | 代价 |
|---|---|---|---|
| **A 切图** ✅ | 把**当前图换成旧图**，新图丢掉 | 加一个 `Atlas::SetCurrentMap()` | 重定位前那段路丢了 |
| B 真合并 | 算出两图变换、合成一张 | **高**（要 Sim3 估尺度；ORB-SLAM3 最糙的部分；而且它靠回环自动触发，要人工触发得绕过 LoopClosing 判据） | 见下 |

**选 A 的理由不是"容易"，是 B 想解决的问题在 A 的语义下不存在。**

B 多出来的价值只是「保住重定位前那段路」——而那段路恰恰是"我从门口走进商场"
那几步，**本来就不想要**（它在新图坐标系里，和旧图对不齐）。

**⚠️ 切图时轨迹必须清零。** 切图前的轨迹点在**新图坐标系**里，切图后的是
**旧图坐标系**。两份没有对齐关系（那个关系只有 LoopClosing 回环合并时才有），
硬接上去轨迹会跳。**清零是唯一诚实的选择**，而且符合语义：
按重定位的意思就是「**从这里开始**」。

## 4. 路径点，与重定位

### 4.1 什么是路径点

**一条记录：`{ 名字, 位姿 }`。** 就是你此刻站的地方。

> **📌 2026-09-30 更正。** 这一节原先叫「锚点」，而且**被写成了为「重定位」服务的机制** ——
> 那是我把用户的一个**临时思路**当成了功能。用户原话：
> 「是为了解决混淆场景重定位问题时，我提出人为的在没有混淆场景进行重定位，
> **没有把它做进功能的打算**」。
>
> **用户本意是「路径点」，为了导航。** 而这两个概念**在 UI 上其实是同一个东西**，见下。

**它在界面上只有一副样子：2D 地图上的一个点。** 但可以有**两种用法**：

| 用法 | 怎么用 | 需要什么 |
|---|---|---|
| **导航**（本意） | 2D 地图上看着它走 | `{名字, 位姿}` |
| **提示该在哪重定位** | 走到它附近再按「重定位」 | 同上 |

**⭐ 「记一个路径点」= 记下当前位姿 + 起个名。** 位姿从 `nativeGetPose()` 直接拿 ——
**不需要用户摆放，也不需要新数据结构**。而且它必然落在轨迹上：
**你站过的地方，就是轨迹上的一个点。**

> **2026-10-20 实现时改了存法。** 不存世界坐标，而是**锚在一个关键帧上、存相对位姿**
> （`T_rel = Tcw_此刻 * Twc_锚点`）—— 和轨迹完全同一套。理由：BA / 回环 / 合并会挪整张图，
> 存死的坐标会自己漂走。锚 KF 之后，合并时 `pKF->UpdateMap()` 搬的是对象指针，路径点自动跟过去；
> 锚点被剔就沿 `mTcp` 爬到活着的父帧；只有 `GetMap() == nullptr`（地图被重置）才失效。
> ⚠️ 锚点要用 `Map::GetLatestKeyFrame()`（图集合里最新），**不能用 `Tracking::GetLastKeyFrame()`**
> —— 后者可能还在 `LocalMapping` 队列里，而 `Release()` 会直接 delete 排队的 KF。

### 4.2 第 2 层（限制重定位候选范围）**先不做**

| 层 | 做什么 | 成本 |
|---|---|---|
| **第 1 层** | 路径点只是**给人看的标记** | **零上游改动** ✅ **做** |
| 第 2 层 | 重定位时**只在路径点附近搜候选**（改 `DetectRelocalizationCandidates` 的范围） | **要改上游** ❌ **先不做** |

**第 1 层零成本，而且已经解决主要问题 —— 用户知道该在哪按。**

**第 2 层先不做**，两个理由：

1. **它只在「大而重复的场景」（商场、停车场）才有价值** —— 房间尺度用不上
2. **有更便宜的兜底**：§4.5 那条「按完重定位在 2D 地图上标出定到哪了，让用户确认」

> **触发条件：等你真的撞上「明明按了重定位却定到别处」，再做第 2 层。**
> 在那之前它是过度设计。

**路径点可以多放**：电梯口、楼梯口、商场入口各一个，每个把长路径**切成短段**。
段越短，累积漂移越小。

### 4.3 重定位是**显式按钮**，不是自动的

这是本设计里最实质的一个简化，它一次解决三个问题：

| 自动（启动即重定位） | 手动按钮 |
|---|---|
| 要改 `Tracking` 的启动路径 | 不用碰 |
| 要设计失败回退路径 | 失败就再按一次 |
| 要写「什么时候该切」的自动判据 | **场景选择交给站在现场的人** |

**失败代价从「整个会话废掉」降到「再走两步按一次」。**

### 4.4 失败提示要分情况

| 失败 | 真实含义 | 提示 |
|---|---|---|
| DB 里没候选 | **你不在旧图覆盖的地方** | 「这里没扫过，走到之前建过图的地方再试」 |
| 有候选但匹配不上 | 场景变了 / 光线变了 / 角度太偏 | 「换个角度或走近一点再试」 |
| 当前图是空的 | **代码问题**（候选被 `pMap` 过滤挡住） | 不该让用户看到 |

### 4.5 第四种情况：成功了但定错了

**感知混淆** —— 重定位"成功"了，但定到了错误的地方。

> **它比"定不上"危险得多，因为算法自己不知道错了。**
> 一排长得一样的柱子，词袋匹配给出一批候选，PnP+RANSAC **成功地**解出一个位姿——
> **RANSAC 的成功判据是内点数，不是"这真的是同一个地方"**。一条柱子对上另一条柱子，
> 几何是自洽的。**这就是「重定位的结果必须让人看一眼确认」这条设计的全部理由。**

> （对照：**弱纹理**（白墙、水泥）是"点太少"，表现为**跟踪丢失**——会报错、能察觉。
> 感知混淆是"点很多但全错"，**不报错**。两者都要防，但后者才是墙。）

**用户怎么知道？看 2D 地图。** 如果标出的位置明显不对（他刚进商场，
却显示在停车场另一头），一眼就看出来了。

**所以：按完按钮要在 2D 地图上标出「重定位到的位置」，让用户确认**
（可以给个"不对，重来"）。

这不是把算法的责任推给用户——在感知混淆无解的前提下，**人是最好的判断者**：
他知道自己刚走进商场还是刚走进停车场。**这和测距那条「人指示 + 算法吸附」
是同一个哲学。**

> ⚠️ **一个要纠正的直觉**：「关掉回环检测就没有混淆问题」**不对**。
> 关回环消除的是「**错的回环把整张地图掰歪**」（LoopClosing 线程）；
> **重定位的混淆是另一回事**（Tracking 线程拿当前帧查 DB，匹配到长得像的旧帧）。
> 两者都要防，但机制不同。**场景选择防的是后者。**

## 5. 2D 地图与轨迹记录

> **⚠️ 排期（2026-09-28）**：这一节是**设计**，一直没排进任何里程碑。现在定：
> **挂在 M5 之后** —— 位姿有了就能先画轨迹，点云快照再加。
>
> **但它有一个结构性依赖，现在就要留位置**：`SlamEngine` 上「**在 SLAM 线程上取一次
> 深拷贝快照**」那个接口。它已经在 [STAGE5](STAGE5_JNI_BRIDGE.md) §6 的
> `SlamEngine` 形状里预留了（连同两条硬约束：必须跑在 SLAM 线程、必须深拷贝）。
> **这一步不写实现**，只是别让那个形状被改掉。

### 5.1 画什么

| 元素 | 数据来源 |
|---|---|
| **轨迹**（走过的路） | 每帧的 `Twc.translation()`（或关键帧位置连线） |
| **当前位置** | 当前 `Twc.translation()` |
| **路径点** | §4 那些标记（导航用） |
| **最近一次重定位的结果** | §4.5 的验证手段——**显示本身就是验证** |

### 5.2 投影是**白送的**：直接投到 XY 平面

因为用的是 **Mono-Inertial**，地图在惯性初始化完成时会被**整体旋到重力对齐、
并施加米制尺度**（LocalMapping.cc:1282）：

```cpp
Sophus::SE3f Twg(mRwg.cast<float>().transpose(), Eigen::Vector3f::Zero());
mpAtlas->GetCurrentMap()->ApplyScaledRotation(Twg, mScale, true);
```

于是：

- **世界坐标系的 Z 轴就是竖直方向** ⟹ **水平面 = XY 平面**，投影过去就行，不用自己估
- **单位是米** ⟹ 比例尺直接是米

纯单目这两样都得自己求。**这是 Mono-Inertial 白送的好处，而它就是「2D 地图」
的前提**——用之前要知道它从哪来。

### 5.3 z 怎么处理，边界怎么定

**这一节的结论是「先都不做」** —— 但把选项记下来，免得下次重新推一遍。

#### 「墙」在稀疏地图里**不存在**

ORB-SLAM3 的地图是**离散点云**，**点与点之间是空的**。没有任何东西表示"这里是实体"。
**所以「边界」不是能读出来的属性，要自己造。**

| 层次 | 做法 | 代价 | 结果 |
|---|---|---|---|
| **不做边界** ✅ | 只画点，让"哪里有点"自己浮现形状 | **零** | 斑驳的点云俯视图 |
| 做边界 | 栅格化 + 膨胀 / 占据栅格 / alpha shape | 中到大 | 像平面图，但仍有大量空洞 |

**先做前者。而且"斑驳"才是诚实的** —— 你扫过的那面墙，确实只有二三十个点被看到。
**膨胀成一条实线是在假装。**

这和 [MAP_FEATURE_IDEAS](MAP_FEATURE_IDEAS.md) §7 那条「**"未扫描"的定义必须诚实**」
是同一个判断：**不假装知道墙在哪，只显示"我在哪看到过点"。**

#### z 应该是**区间**，不是单个平面

| 做法 | 结果 |
|---|---|
| 单个 z 平面（薄片） | ❌ 稀疏点云在薄片里几乎没点，等于什么都没画 |
| 投影全部点（不限 z） | ⚠️ 地板糊成一大片，把图糊死 |
| **z 区间**（排除地板和天花板） | ✅ 最像平面图 |

**但有个前提问题：z 的零点在哪？** 重力对齐给的是 **Z 轴方向**，
而**原点是做惯性初始化时的位置**，**不一定是地面**。

| 解法 | 代价 | 前提 |
|---|---|---|
| 用初始化时的相机高度当基准 | 低 | 假设眼高 ~1.5 m，**不一定成立** |
| 让用户标一次"地面在哪" | 低 | 多一次交互 |
| **先做高度着色** ✅ | **零** | 投影全部点，按 z 上色（低处蓝、高处红） |

**先做高度着色**：地板一片蓝、墙是蓝→红渐变、柱子是竖直色带 ——
**零前提，一眼看出结构**，而且不用回答"哪个 z 是地面"。

（顺带：`T_b_c1` 的平移是 0、**相机到 IMU 的杆臂没标**，所以"相机高度 = 眼高"
本身还有几厘米误差，拿它当 z 基准不划算。）

#### 画布范围

**按地图点的包围盒自适应 + 一点余量**，轨迹走出去就扩。
路径点和当前位置在同一坐标系里，不用单独处理。

### 5.4 从「轨迹图」起步，不做栅格

| 做法 | 工程量 | 效果 |
|---|---|---|
| **关键帧位置连成线（轨迹图）** | **极小** | 信息量低，但立刻可用，零新算法 |
| 地图点栅格化 + 膨胀 | 中 | 像平面图，但仍有大量空洞 |
| 建占据栅格 + 通道拓扑 | 大 | 导航能用，但这已经是新算法 |

**先做轨迹图版本**：它验证整条链路（读地图 → 变换 → 渲染），零新算法。

> **📌 2026-09-30 补充：第三档不只是「工程量大」，是前提不成立。**
>
> 查过文献 —— 稀疏 SLAM 图变可导航占据图的标准做法是 **OctoMap（八叉树 + 概率占据）**，
> 但**做成的案例全都要求稠密点云**（RGB-D / 深度相机 / 双目）。一篇 ORB-SLAM3
> [源码分析](https://blog.csdn.net/ruanjian_gc/article/details/145282817)说得直白：
> **「稀疏地图只能用于定位，不能直接用于导航」**。
>
> **我们是纯单目，没有深度源。** 补深度只有三条路，每条都不便宜：
>
> | 途径 | 代价 |
> |---|---|
> | 换/加深度相机 | 硬件 |
> | 双目 | 改采集端，两路同步 |
> | 单目深度估计网络 | 要跑网络，而且**深度是相对尺度**，还得跟 SLAM 的米制尺度对齐 |
>
> **就算补上，稀疏点光线投射出来的图也大半是 unknown** —— 换一张「建议可通行区域」级别的图。
>
> **⭐ 而「轨迹即路线」不是权宜之计** —— 它对应文献里一个成熟方向：
> **teach-and-repeat**（教一遍、走一遍）。它的两条核心洞见正好对上我们的处境：
> 「**朝向比位置好估**」和「**走过的路径本身就是路线，不需要路径规划**」，
> 而且有理论结果支持（只修朝向、位置交给里程计，即可抑制误差发散）。
>
> **它的难点在「没有全局图 / 不知道位置 / 要自主控制」这三件事上 —— 我们一件都不缺**
> （ORB-SLAM3 给全局一致图、一直跟踪位姿、人在回路）。
> **所以只借它的洞见，不移植它的机制。**

> 这里的「栅格化」和 §5.3 的边界**是同一个技术，回答的是不同问题**：
> §5.3 问「要不要造墙」，这里问「从哪一档起步」。

### 5.5 轨迹记录是一个开关，默认**开**

- **成本极低**：每帧存 7 个 float（位置 + 四元数），30 fps 下一分钟约 **50 KB**
  —— 比 PNG 落盘轻**四个数量级**
- **默认开**：它是"事后能不能回看"的唯一来源。默认关的话，多半会忘记开，
  等想回看时发现没有
- **一次性的建图不保存路径** —— 路径**单独保存**，可以事后调用查看，
  **不跟地图文件绑死**

#### ⚠️ 必须存 **3D**，不能存投影后的 2D

记录的是 `Twc.translation()`，**三个坐标**。**2D 图只是它的一个投影。**

**所以换 z 区间、换着色方式，路径重新投影一次就行，记录本身不动。**

**反过来推**：如果只存投影后的 2D 坐标，换 z 区间就**真丢了信息**。

> **规则：记录事实（3D 位姿），显示是策略（怎么投影）。**
> 和 09-21 那条「事实归模块，策略归编排层」是同一个道理。

**顺带一个好处**：3D 记录意味着**上下楼时轨迹不重叠**（2D 投影会重叠），
所以「迷宫路线记录」在 3D 里也成立 —— **2D 只是"看"的一种方式，不是数据本身。**

### 5.6 和「录制落盘」的区别

两者都是"存东西"，但**完全不同的量级和目的**，是**两个开关**：

| | 记录路径 | 录制落盘 |
|---|---|---|
| 存什么 | 位姿序列（**几十 KB/分钟**） | 灰度 PNG（**几 MB/秒**） |
| 干什么用 | 回看走过的路 | **取证**——手机上出问题时拉回 PC 跑 |
| 默认 | **开** | **关**（高级功能） |
| 生命周期 | 跟会话 | **跟已有的「准备/录制」状态机** |

## 6. 开关，两个挂点

### 6.1 SLAM 这条线内的开关

| 开关 | 取值 | 谁控制 |
|---|---|---|
| **地图来源** | 载入 / 新建 | 入口页定一次 |
| **视图** | 2D 地图 / 测距 | 随时切 |
| **记录路径** | 开 / 关 | 按钮，**默认开** |
| **录制落盘** | 开 / 关 | **抽屉里的开关，默认关**（2026-09-28 加回） |
| **实时测距** | 开 / 关 | **抽屉里的开关，默认关**（2026-10-07 加） |

后两个开关**记进 `SharedPreferences`**，下次进来还是上次的状态。

**为什么不做成一个 enum**：它们两两之间没有必然联系。真实会出现的组合：

- **建图但不看轨迹** —— 走一圈看覆盖够不够
- **建图且录制** —— **跑 SLAM 的时候顺手录一段**，拿同样的数据去 PC 上跑对照（见 §6.2）
- **录但不建图** —— 走「录制模式」那条独立入口

做成 enum 的话这些组合表达不出来，只能靠特例。

### 6.2 ⭐ 落盘不是「模式」，是「消费者」—— 它有两个挂点（2026-09-28 定）

```
录制模式        相机 → 落盘
SLAM 页 + 开关  相机 → SLAM + 落盘
```

**同一份落盘逻辑（`SessionWriter`），挂在两个不同的相机所有者下面。**
它自己不拥有相机，只是被喂帧。

**这和 09-27 那条「两个模式互斥」不矛盾** —— 那条针对的是
**「两个模式各自开相机」**：

| | 有几个相机所有者 | 碰不碰对焦 | 允许吗 |
|---|---|---|---|
| 录制模式 ↔ SLAM 页（同时开） | **2 个** | 都想要 | ❌ 互斥（§6.3） |
| SLAM 页内部挂一个落盘消费者 | **1 个** | 不碰（只消费帧） | ✅ 允许 |

**为什么最后需要它**：M6 的验收要「**同一段数据**，手机跑一遍、PC 跑一遍」——
不边跑边录，手机那次就没留下任何数据（见 [STAGE5](STAGE5_JNI_BRIDGE.md) M6）。

**代价**：开着录制时 SLAM 的帧率会掉（要写 PNG）。**这是刻意的，而且对照仍然成立** ——
录下来的就是手机喂进去的同一段序列。**但要实测「掉到多少会跟丢」**，那是 M6 的验收项。

### 6.3 两个模式仍然互斥：对焦所有权

录制模式（独立入口，不跑 SLAM）和 SLAM 页**不能同时开着相机**。原因两条：

| 原因 | 具体 |
|---|---|
| **对焦所有权** | `CameraCapture.beginSettle()` 是「先收敛、再把 AF 锁死」。而**锁焦的另一个后果是：fx 只在那个对焦距离上等于 435.2**。两个所有者的**对焦策略直接冲突** —— 录制每次「开始准备」都要重新收敛，而 SLAM 一旦跑起来**绝不能被重新对焦打断**（位姿会跳） |
| **性能** | 两个都吃满相机和 CPU，叠一起两个都做不好 —— 而**帧率稳不稳正是录制那套的判据之一**（重录做 A/B 对比要看它） |

**所以「或」语义的硬件类（旧 §7.1）不成立** —— 它要解决的是"两个申请者"，
而正确做法是**根本不让两个所有者同时存在**。**两个页面各自持有自己的
`CameraCapture` / `ImuCollector`。**

### 6.4 采集端的状态机没变

`IDLE ─开始准备→ ARMED ⇄ RECORDING` 整个搬到 [CaptureActivity] 里，
**逻辑一行没改**。它的「准备」现在**真的就是它自己的准备**（不再和 SLAM 共享），
所以旧 §7.1 那句「相机/IMU 从它身上挪走」也一并作废了。见
[changes/2026-09-21](../changes/2026-09-21-camera-preview-and-gating.md)。

## 7. 生命周期与资源挂载

### 7.1 相机和 IMU 归**当前那个页面**（2026-09-27 定）

09-21 把相机和 IMU 绑在「准备」上，理由是"两条线的开销都由那个按钮正当化"。
后来一度改成「一个『或』语义的共享硬件类」，**现在撤回了** —— 见下。

| 资源 | 谁管 |
|---|---|
| 相机 + IMU | **当前那个页面的编排层**。SLAM 页的「启动 SLAM」、录制页的「开始准备」各自持有，互不共享 |
| 落盘 | 录制页的「录制」（不变） |
| `System` / 地图 | `SlamEngine`（进程级，跨「停止」保留） |

#### ❌ 撤回：相机和 IMU **不**归一个共享的类管（2026-09-27 晚些时候改）

**这一节本来写的是「一个『或』语义的硬件类，SLAM / 录制两个申请者，任一需要就开」。**
**它作废了** —— 因为 §6.3 定下「**两个相机所有者不能同时存在**」，申请者不该有两个，
「或」没有意义了。

**现在：两个页面各自持有自己的 `CameraCapture` / `ImuCollector` / `PreviewView`。**

各自持有能成立，是因为**它们永远不会同时开着**：从 SLAM 页进录制页，SLAM 页会
`onStop`（相机随之关掉）；反过来也一样。所以不存在"两个所有者抢同一颗镜组"。

**相机/IMU 的所有者就是「当前那个页面」**，没有什么中间层。

**地图（`System`）从来不在这个讨论里** —— 判据是 §5 决策一那条：
**耗电的资源跟着用户意图走，耗时的资源跟着进程走**。相机/IMU 是耗电的，停就该关；
`System` 重来要等 145 MB 词袋，跨「停止」要一直留着。它归 `SlamEngine`。

> ⚠️ **代价**：两个页面的相机装配代码会各有一份（`camThread` + `cam` + `imu` + `preview`
> 的接线约 50 行）。等 M5 两个页面都要真开相机了，再看要不要抽出来共用 ——
> 那时候才知道两边的装配到底像不像。

### 7.2 两个状态

```
未启动 ──[ 启动 SLAM ]──► 运行中
   ▲                        │
   └────[ 停止 / onStop ]───┘
```

| SLAM | 录制 | 相机 | IMU | `System` 对象 | 地图 |
|---|---|---|---|---|---|
| 未启动 | 没录 | 关 | 注销 | **保留**（如果构造过） | 保留，成为「旧图」 |
| 未启动 | **录制中** | **开** | **注册** | 保留 | 保留（不动） |
| 运行中 | 没录 | 开 | 注册 | 活着 | 在长 |
| 运行中 | **录制中** | 开 | 注册 | 活着 | 在长 |

**前两列是正交的**（§6 那四个开关里的两个）。相机/IMU 那两列由「或」决定 ——
只要 SLAM 开着**或**录制开着，它就是「开」。表里第二行就是 §6 说的「**录但不建图**」。

**`System` 对象跨「停止」保留** —— 这是不复付词袋加载代价的唯一办法
（否则每次开关都要等十几到几十秒）。这件事由 §2.6 的 `SlamEngine` 负责。

### 7.3 「停止」不等于「保存」

- **「停止」** → 关相机 / IMU / 喂帧；`System` 保留，地图成为「旧图」（见 §2.3）
- **`onStop`（切后台）** → 等同「停止」。**录制文件一律保留**（录到一半也是真数据）
- **存盘**是另一件事 —— 见 §9

### 7.4 词袋加载

- **139 MB 文本，实测本机 37.7 s**（2026-09-27），必须异步，**「启动」时界面要给进度提示**
- **只加载一次**：`System` 构造一次之后跨「停止」保留
- 本版本**只有文本加载路径**（`System.cc` 只调 `loadFromTextFile`），没有二进制快速路径
- **载入旧图**时词袋照样要加载（atlas 里只有校验和，不含词袋）

## 8. 测距的位置

**不是模式** —— 它需要 SLAM 在跑（要位姿），和 2D 地图是**同一条流水线的两个视图**。

> **📌 2026-10-07 修订：第一版做成了抽屉里的「实时测距」开关，不是「从『其他功能』进的视图」。**
> 用户提的：**「测距是一个功能开关和录像一样」**。而且十字只是**叠在预览上的一层**，
> 没必要为它切走视图。**开关默认关，状态记进 `SharedPreferences`。**
> 「视图」那个形态（专门的测距页 + 按钮栏）留给 (b) 两点距离那一步。

| 交互 | 做什么 | 状态 |
|---|---|---|
| **实时读数** | 画面中心**十字**；能测就把距离直接显示在十字旁边（零操作） | **✅ 已实现**（真机未跑） |
| **添加标记点** | 按下 → 定一个点（吸附到地图点）；移动手机把十字移到第二点 → 确定 → 显示距离与直线 | 未做 |

**配套**：吸附目标要在画面上高亮（让你知道"确定"会定到哪）**✅ 已实现（琥珀色小圈）**；
读数要做平滑（否则跳得看不清）**✅ 已实现（最近 5 帧取中值）**；
第一点移出视野时要在边缘指示、要能撤销 —— **未做**（都是 (b) 才需要的）。

**可测性**：能测就出数字；**测不了时必须给一句话**（"对准有纹理的地方"），
**不能沉默**——沉默和"测不了"要能区分。**✅ 已实现**，而且分成了**四档**：
`等待跟踪…` / `对准有纹理的地方` / `≈ x.xx m（不太准）` / `x.xx m`。
**头两档一定要分开** —— 「跟踪还没就绪」和「这个地方测不了」是两件事，
混在一起用户会去擦镜头。

**时效性**：`MapChanged()` 触发时提示「地图刚被优化，之前的测量可能需要重算」。**未做。**

**测量结果不保存**（2026-09-26 定）。**返回主界面时测量会话保留**
（量到一半去看地图，回来点还在）。

实现细节见 [STAGE6_MEASUREMENT.md](STAGE6_MEASUREMENT.md)。

## 9. 保存策略

> ⚠️ **这一节只定了「存成什么」，没有定「什么时候存」。** 见 §10「还没定的」那一条 ——
> 那是个洞，M8 之前必须补。

**一个会话存成一组文件，不是单个 `.osa`。**

```
<名字>.osa              地图（ORB-SLAM3 的格式，我们只读不写）
<名字>.waypoints.tsv    路径点（§4）
<名字>.path.csv         路径
```

**⚠️ 「我们造的概念」不进 `.osa`。** 那是 ORB-SLAM3 的格式，**写它就得改上游的
序列化**（13 个文件的 `serialize()`，见 [MAP_FEATURE_IDEAS](MAP_FEATURE_IDEAS.md) §4）。
**路径点、路径都是我们自己的概念，单独存就行** —— 同名不同后缀，互不干涉。

> **2026-10-20 落实**：路径点用的就是 `<名字>.waypoints.tsv`（不是原先写的 `.markers.json`）。
> 选 TSV 是因为**读写都在 C++ 侧**，为固定 schema 手写 JSON 解析器不值当。

**会话目录（2026-10-21 落实）。** 一个 atlas 里可能有好几张图，轨迹按图分文件夹：

```
maps/<会话目录>/
├── <会话名>.osa        整个 atlas
├── session.json
├── map-7/             一张 atlas 图一个文件夹 —— 里面的轨迹**全部同一坐标系**
├── traj/              还没归档的（这一趟没存图 / 存失败）
└── rec/               录像
```

`map-<id>` 用**合并之后活着的那张图**的 id。合并**改坐标系、不改图的身份**：
存活目录里的存量轨迹乘 `T_on`，被吸收目录原样并进来再删掉 —— 文件夹数量始终等于
`.osa` 里活着的图数。详见
[2026-10-21-map-folders-for-trajectory.md](../changes/2026-10-21-map-folders-for-trajectory.md)。

**小地图的历史轨迹层（2026-10-21）。** 只叠**当前轨迹所属那张图**的
`map-<id>/traj-*.txt` —— 小地图的位姿、点云、白线都是当前图的系，别的图各有一个原点。
合并发生、还没存图的那段窗口里，被吸收目录原样画、幸存图那一族乘 `T_on`
（多跳按链累积）⟹ 合并完成的那一刻，载入那张图的历史轨迹就出现了。
抽屉里有总开关，管理页能逐条隐藏 / 删除。详见
[2026-10-21-minimap-history-tracks.md](../changes/2026-10-21-minimap-history-tracks.md)。

**2D 地图查看器（2026-10-24）。** 抽屉里的「地图查看」是全屏 2D 地图：atlas 里
**有 KF 的图都能选**，**即使还没和当前图合并**。一次只看一张 —— 不同图没有公共坐标系，
不能叠。每张图画自己的点云、`map-<id>/` 的历史轨迹、该图的路标点；只有当前轨迹所属
那张图才画当前位置。单指拖动、双指捏合、`+`/`−`/`适应`；切片中心可以在「当前高度 /
点云 z 中位数」之间切。详见
[2026-10-24-map-viewer.md](../changes/2026-10-24-map-viewer.md)。

**默认「另存」，不覆盖。** 理由：自用场景磁盘不紧张，而**覆盖之后就回不去了**
——万一这次建得比上次差（漂移大、跟丢多），没法回头。

**⚠️ 「覆盖」的前提是两张图已经对齐。** 走了方案 A（切图）之后没有对齐关系，
文件里就是**两张互不相干的图**——这时"覆盖"只是把两张无关的图塞进一个文件。
所以覆盖这个选项**在 A 方案下要谨慎给**。

## 10. 还没定的

- **路线导航**：**2026-09-30 定了 A 方案** —— 2D 地图上同时画「你在哪」和「路径点在哪」，
  **人看着走**，不做路径规划。理由见 §5.4：稀疏点云不构成可通行空间，
  而「沿走过的路走」对应文献里成熟的 teach-and-repeat 方向。
  **「原路返回」只要轨迹**（零新算法）。
- **旧图过期怎么处理**：ORB-SLAM3 里没有这个概念。自用场景（自己家 / 常去的商场）
  变化慢，暂时按"不管"处理，但要知道它存在。
- ~~**「停止」之后恢复时，位姿怎么接**：倾向启动后自动重定位。~~
  **作废（2026-09-27）**：§4.3 已经定案「重定位是**显式按钮**，不是自动的」，
  而那是最实质的一条简化。这一行是它之前的残留，两条直接打架 —— 以 §4.3 为准。
- **保存什么时候触发**：§9 定了文件格式和「默认另存」，但**没有一个字说什么时候写**。
  §7.3 宣告了「停止 ≠ 保存」并指向 §9，而 §9 没回答。按现有文档，
  磁盘上的 `.osa` 只在**进程退出**时由上游 `Shutdown()` 自动产生 —— 在 Android 上不可靠。
  **这是个洞，M8 之前必须补。**
- **多张旧图怎么选**：目前只说"挑关键帧最多的那张"，多张同名/同场景的情况没处理。
