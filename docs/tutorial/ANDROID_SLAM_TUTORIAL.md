## 1. 关键认知

这一节的两条**在实现全换掉之后仍然成立**，所以留在本文。

### 1.1 为什么必须 Mono-Inertial

| 模式 | 有米制尺度吗 | 能测距吗 |
|---|---|---|
| `mono_*`（纯单目） | ❌ up-to-scale | ❌ |
| `mono_inertial_*` | ✅ IMU 初始化后恢复 | ✅ |
| `rgbd_*` | ✅ 深度图直接给 | ✅（但手机上没深度源） |

纯单目 SLAM 的轨迹形状正确、整体大小任意，量出来的"距离"没有单位。
**要测距就必须有米制尺度，所以必须 Mono-Inertial。**

原理：加速度计测的是**真实的 m/s²**，在运动激励足够时（相机有平移和旋转）可以解算
尺度与重力方向。这个过程叫**惯性初始化**，ORB-SLAM3 里大约需要 2–15 秒的移动。

> **推论（决定了 UI 长什么样）**：初始化完成前不能测距。UI 必须明确指示状态，
> 而且**要主动引导用户运动**——静止举着手机初始化不了。

### 1.2 ORB-SLAM3 的坐标系约定必须实测

| 概念 | 含义 |
|---|---|
| `Tcw` | world → camera |
| `Twc` | camera → world，`Twc = Tcw.inverse()` |
| 相机中心 | `C = Twc.translation()` |
| OpenCV 相机坐标 | x 右、y 下、z 前 |

`TrackMonocular()` 返回 `Sophus::SE3f`。**它到底是 Tcw 还是 Twc，不要靠记忆，要实测**：
把手机朝前平移 30cm，看 translation 变化的是哪一轴、变号没有。
**这一步花 10 分钟，能省掉后面几天的调试。**

## 2. 阶段一：PC 跑通 Mono-Inertial

**目标**：在 PC 上用公开数据集确认 ORB-SLAM3 的 Mono-Inertial 通路是好的。

**关键决策**

- **先用公开数据集，不用自己的数据。** 这一阶段要建立的判据是「什么是正常的轨迹」，
  拿一个已知答案（EuRoC 有 ground truth）来标定这个判断，后面才有的比。
- **选 Mono-Inertial 而不是 Mono。** 见 §1.1。

**验收判据**

| 现象 | 结论 |
|---|---|
| 轨迹与 ground truth 尺度对得上（ATE RMSE 几十厘米量级，不是几米） | ✅ 尺度恢复，通路正常 |
| 尺度差几倍 | ❌ 多半是 IMU 噪声参数或时间戳口径 |

**详情**：[PC_ORBSLAM3_WORKFLOW.md](PC_ORBSLAM3_WORKFLOW.md)（下载数据集、跑、
`mono_inertial_euroc` 的参数约定、用 evo 看轨迹）

## 3. 阶段二：Android 采集层

**目标**：App 只做「采集 + 落盘」，不做 SLAM。把数据拿到 PC 上验证。

**关键决策**

| 决策 | 为什么 |
|---|---|
| 关 EIS（视频防抖） | 会裁切并变形画面，**直接毁掉标定** |
| 关 OIS（光学防抖） | 同上，且改变有效内参 |
| 锁死对焦（`AF_MODE_OFF` + 显式 `LENS_FOCUS_DISTANCE`） | 对焦呼吸会改变焦距；但**只发 `AF_MODE_OFF` 会让 HAL 把镜组驱动回停泊位**——这是本工程最贵的坑 |
| 锁定主摄，不用超广角/长焦 | 焦距和视场角都不对 |
| 锁死 Activity 方向 | IMU 坐标系随屏幕旋转而变，轴会跳变 |
| 固定帧率 | ORB-SLAM3 需要稳定帧率 |

**时间戳是整个方案的地基**：`Image.getTimestamp()` 与 `SensorEvent.timestamp`
**天然同基准**（`CLOCK_BOOTTIME`），所以**直接用，不做任何转换**。
绝不要混进 `System.currentTimeMillis()` 那类 wall-clock。

**验收判据**

| 现象 | 结论 |
|---|---|
| `frames_dropped` = 0、`imu_dropped` = 0 | ✅ 采集链路没有瓶颈 |
| IMU 的第一条时间戳**小于**相机第一帧，且差约 0.3 秒 | ✅ 两个流的时间关系正确 |
| 帧率稳在 30 fps | ✅ |

**详情**：[STAGE2_ANDROID_CAPTURE.md](STAGE2_ANDROID_CAPTURE.md)（环境搭建、
每个源文件的职责与踩坑、无线调试、故障排查）

## 4. 阶段三：PC 验证采集数据

**目标**：把「算法问题」和「采集问题」彻底分开。**这一步不能跳过。**

**关键决策**

- **先录一段 60 秒以上、前 15 秒持续平移的数据再跑 SLAM。** 惯性初始化是一条挂在
  时间梯子上的状态机，激励不足时会陷入「重置 → 更爬不出来」的自我循环。
  这条是拿几十次失败跑换来的。
- **判据不只看"有没有出轨迹"，还看轨迹体检**：关键帧数、位姿覆盖率、重置次数、
  VIBA2 有没有跑过。

**验收判据**

| 现象 | 结论 |
|---|---|
| 跑完并出轨迹，关键帧数正常，重置都能恢复 | ✅ 采集没问题，可以进入阶段五 |
| CPU 单核空转、不输出 | ❌ 老版 ORB-SLAM3 的 `while(!eof())` 死循环，见 §9 |
| `IMU 与相机时间关系不满足前提` | ❌ 采集侧的问题，回阶段二 |

**详情**：[PC_ORBSLAM3_WORKFLOW.md](PC_ORBSLAM3_WORKFLOW.md)（跑自采数据、判读日志）
＋ [ORB_SLAM3_TRACKING_FLOW.md](ORB_SLAM3_TRACKING_FLOW.md)（线程模型、
从 `main()` 起的调用链、**地图重置的四条路径**）

## 5. 阶段四：相机与 IMU 标定

**目标**：拿到能喂给 ORB-SLAM3 的内参、外参和噪声参数。

标定提供三样东西：**相机内参 + 畸变**（决定反投影射线的方向）、
**相机-IMU 外参**（把两套坐标系统一起来）、**IMU 噪声参数**（决定融合权重）。

**关键决策**

- **不用 Kalibr。** 它只支持 ROS 1，而 ROS 1 到 Ubuntu 20.04 为止——
  在这台 24.04 上装不了。改用 **OpenCV + ChArUco**。
  （旧版本教程里写的 Kalibr + rosbag 流程是**走不通的路**，已废弃。）
- **内参的最终判据是"真值判据"，不是"标定内部指标"。** 三次标定的 fx 抖在
  435.2 / 439.2 / 452.3，组内子集重标又各自稳定——内部指标分不出谁对。
  最后靠**已知长度的物体斜放、三角化量距离**裁定。
- **判据的强弱完全取决于标记怎么摆。** 横平摆放灵敏度 0.08x 测不出东西；
  一近一远斜放才有 1.93x。这条花了两次失败才认下来。
- **"尺度误差会伪装成 fx 误差"。** 距离判据必须先扣掉轨迹尺度，否则会得出一个
  看似合理的假 fx。**重投影极小值才是与尺度无关的判据。**
- **IMU 噪声用 Allan 方差实测，不用 datasheet、不用猜。** 实测结果：
  `NoiseGyro` 的原估计值**高估了 19 倍**——偏大的预积分协方差会让优化器过度不信陀螺。
- **Walk 两项保持估计值。** 17.8 分钟的静置只到 Allan 曲线的平顶段（bias 不稳定区），
  没进 +1/2 上升段，硬算出来的游走系数取决于窗口位置，没有意义。

**验收判据**

| 项 | 判据 |
|---|---|
| 内参 fx | 真值判据（重投影尖底 + 已知长度三角化）裁定为 **435.2** |
| 尺度 | 已知 1.6m 物体，SLAM 轨迹量出的距离 **≈ 0 ± 2%**，无系统性偏差证据 |
| IMU 白噪声 | Allan 拟合六轴斜率全 -0.50，轴间一致性 Gyro 7% / Acc 25% |

**已知没做的两项**（都不堵阶段五/六，但要知道它们存在）：外参**平移**仍为 0、
畸变系数未测出。

**详情**：[STAGE4_CALIBRATION.md](STAGE4_CALIBRATION.md)（标定板、采集要求、
脚本用法、怎么看结果）

## 6. 阶段五：JNI 桥接

**目标**：把采集到的帧和 IMU 喂进手机上跑的 ORB-SLAM3，实时拿到位姿。

**关键决策**

- **必须剥离 Pangolin。** 它是桌面 OpenGL 可视化库，Android 上不存在。
  依赖范围比想象中小：`Viewer.cc` / `MapDrawer.cc` 整体替换为空实现、
  `Map.h` 只是 `#include` 没实际用。
- **ORB-SLAM3 必须整体交叉编译。** 不能复用 PC 的 `.so`。
- **三条线程铁律**：相机回调只进队列（绝不在回调里跑 SLAM，会拖垮相机 HAL）；
  队满丢**最旧**的帧（积压会让位姿越来越滞后）；IMU 按时间戳**批量**交给
  `TrackMonocular`（一个样本一次 JNI 调用是反模式）。
- **不动采集端逻辑。** 采集端已经整体锁定（fx、噪声、时间戳口径），阶段五只**加调用**。

**验收判据**

| 项 | 判据 |
|---|---|
| 实时性 | 相机不掉帧；SLAM 跟不上时丢帧不积压 |
| 正确性 | **同段数据手机实时跑 vs PC 跑，轨迹量级一致**（这是唯一的硬判据） |
| 稳定性 | 切后台干净停、回来不崩；连跑 10 分钟不崩 |

**详情**：[STAGE5_JNI_BRIDGE.md](STAGE5_JNI_BRIDGE.md)（**零基础实操**：
NDK/CMake 环境、依赖从哪来、分步里程碑 M0~M8、`SlamEngine` 的实现、ORB-SLAM3 在 Android 上的
特殊失败模式、JNI 坑清单）

## 7. 阶段六：实时尺寸测量

**目标**：在实时画面上点一个点，量出**到目标的距离**；再点一个点，得到两点之间的距离。

**关键决策**

- **深度来自 SLAM 维护的稀疏地图，不是照片本身。**
- **先做「到目标的距离」（一个点）** —— 不需要移动手机、精度更高（单点误差，
  不是两点叠加）。两点距离用**同一套交互**自然延伸（再点一个就多一个数），
  **不需要"选择测量模式"**。
- **吸附到地图点**：手指 ±20 px 压到 1~2 px。而且吸附到的点**是 SLAM 用多个
  关键帧三角化好的结果**，所以「两点离得近、视差不足」的问题在吸附前提下不存在。
- **可测性必须实时反馈**：数据源就是当前帧的跟踪点（几百个，每帧本来就有），
  **不需要全图快照**——所以这个反馈几乎免费。
- **融合取中值不取均值**（对误匹配鲁棒），**离散度大就明确说"测不准"**。

**验收判据**

| 项 | 判据 |
|---|---|
| 精度 | 误差主导项是**位姿误差**，`σ_z ≈ z·δθ`。按「**cm 级 / 相对 2~5%**」规划 |
| 可测性 | 白墙/玻璃/纯色塑料上测不了时**明确说出来**，并提示点边缘和角 |
| 诚实性 | 测不出来时必须说；不确定时给一个**粗略的误差范围**，不能只报随机项 |

**详情**：[STAGE6_MEASUREMENT.md](STAGE6_MEASUREMENT.md)（数据源、吸附、
点击映射、三条路径、置信度、精度与时效）

## 8. 阶段七：UI 状态机

**目标**：让用户永远知道「现在能不能测」，并在不能测的时候知道该做什么。

**关键决策**

- **`NOT_INITIALIZED` 期间禁止测距是硬性要求**——此时没有米制尺度，测出来的数字
  毫无意义。
- **要主动引导运动**，不能只显示一个转圈。惯性初始化需要激励。
- **`GetTimeFromIMUInit()` 是「二值 + 时长」，不是进度条** —— 拿不到"完成到百分之几"，
  所以**别做假进度**，做不确定的动画。
- **测量结果只在该时刻有效**：回环优化会改写历史位姿。`MapChanged()` 触发时
  提示「地图刚被优化，之前的测量可能需要重算」。

**验收判据**

| 跟踪状态 | 测距入口 |
|---|---|
| `NOT_INITIALIZED` | 禁用 + 「正在初始化，请缓慢移动手机」 |
| `OK` | 启用 |
| `RECENTLY_LOST` / `LOST` | 禁用 + 对应的引导文案 |

## 9. 排查手册

跨阶段的经验，不随实现变化，所以留在本文。更细的排查在各自的阶段文档里。

| 症状 | 最可能的原因 |
|---|---|
| **卡在 `LOADED!` 之后，CPU 单核 97% 空转** | 老版 ORB-SLAM3 的 `LoadImages`/`LoadIMU` 里写的是 `while(!f.eof())`。文件打不开时 `getline` 一直失败、`s` 永远是空串，而 `eof()` 永远不会为真（置位的是 **failbit** 不是 eofbit），于是变成死循环。两个加载函数各加一个 `if (!f.is_open()) { cerr << ...; return; }` 就好。常见触发原因：EuRoC 目录约定是 `<seq>/mav0/cam0/data`，而 App 写出来的少一层 `mav0/` |
| **`IMU 与相机时间关系不满足前提`** | IMU 比相机晚开始。ORB-SLAM3 找 `first_imu` 的循环假定 IMU 先开始，没有边界检查，违反前提会读越界内存（**而且不一定崩**，可能只是每帧配到 0 个 IMU 测量、静默给一条烂轨迹） |
| **初始化不了 / 一直 `NOT_INITIALIZED`** | IMU 轴序错了；单位不是 m/s²、rad/s；时间戳不同基准；**或者只是没动** |
| **有轨迹但尺度不对（差几倍）** | IMU 噪声参数错数量级；`T_b_c1` 符号搞反 |
| **轨迹形状对但方向反了** | Tcw/Twc 搞反 |
| **跟踪频繁丢失 / 反复重置** | 激励不足（最常见）；帧率不稳；AE 抖动太大；运动太快；画面纹理太少 |
| **跑几秒后崩溃** | 线程安全问题——在别的线程访问了 SLAM 内部结构；队列没做容量限制 |
| **画面很暗** | AE 锁死了。改成 `TEMPLATE_RECORD` 让 AE 跟随 |
| **测距结果离谱** | 归一化坐标没对齐（高分辨率 vs 跟踪分辨率）；去畸变用了错的内参 |
| **测距结果每次都不一样** | 位姿在漂；或者只用了一条路径没有融合 |
| **PC 上跑得好，手机上不行** | 先看阶段三的判据——十有八九是采集层问题，不是算法 |

### 调试建议

**在 App 里画轨迹。** 实时把 `Tcw` 的位置画成一条线，是最直观的健康指标——
正常应该是平滑的曲线，漂移或跳变一眼就能看出来。

**导出轨迹到 PC 用 evo 对比。** 手机上也能调 `SaveTrajectoryTUM()`，
存到外部存储后拷出来对比。

### 关键 API 速查

```cpp
// 跟踪（IMU 通过参数传入，不是回调）
Sophus::SE3f TrackMonocular(const cv::Mat& im, const double& timestamp,
                            const std::vector<IMU::Point>& vImuMeas = {},
                            std::string filename = "");

// 状态查询
int    GetTrackingState();
bool   isLost();
double GetTimeFromIMUInit();    // 初始化完成前恒为 0；完成后是"距首帧多久"
bool   MapChanged();            // 地图刚被回环 / 合并大改过

// 当前帧的 3D 信息（测距核心）
std::vector<MapPoint*>    GetTrackedMapPoints();      // 与下面平行
std::vector<cv::KeyPoint> GetTrackedKeyPointsUn();    // 已去畸变

// 地图持久化（需要 Boost，见 STAGE5 §3.4）
void SaveAtlas(int type);            // type ∈ {TEXT_FILE, BINARY_FILE}
bool LoadAtlas(int type);
void ActivateLocalizationMode();     // 停 LocalMapping，不再建新关键帧
void DeactivateLocalizationMode();
```

> ⚠️ **`System` 上没有 `GetAllKeyFrames()` / `GetAllMapPoints()`。** 整张地图要通过
> `Map` 拿，而 `System` 没有暴露它（`mpAtlas` 是 private）——**想读地图得自己给
> `System` 加接口**。
>
> 而且别以为加个锁就够了：`Map::GetAllKeyFrames()` 本身**是有锁的**，但返回的是
> **裸指针**，锁一释放就没有任何保护了。**快照必须在 SLAM 线程上取并深拷贝。**
> 详见 [MAP_FEATURE_IDEAS.md](MAP_FEATURE_IDEAS.md) 的「共同前提」一节。

### 关于地图持久化

本版本有 `SaveAtlas()` / `LoadAtlas()`，理论上支持存盘后重新加载并重定位。
**但官方实现比较粗糙，实际用起来可能需要自己加固。** 建议顺序：
先跑通实时跟踪和测距 → 再加持久化 → 如果 `Atlas` 存读不稳定，
退而用 `ActivateLocalizationMode()` 顶住单次会话内的定位。
