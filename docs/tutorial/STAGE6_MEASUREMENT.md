## 0. 先做哪个

两种测量**难度差一个量级**：

| | (a) 到目标的距离 | (b) 两点之间的距离 |
|---|---|---|
| 需要几个点 | **1 个** | 2 个 |
| 误差 | **单点深度误差** | **两个点误差叠加** |
| 实测散布 | — | ±3~4pp（≈5~6cm @1.6m） |
| 像什么 | **激光测距仪** | 卷尺 |
| 状态 | **✅ 已实现** | **✅ 已实现**（真机未跑，2026-10-11）|

## 1. 数据源：两个平行数组

```cpp
std::vector<cv::KeyPoint> GetTrackedKeyPointsUn();   // 当前帧的特征点（已去畸变）
std::vector<MapPoint*>    GetTrackedMapPoints();     // 与之一一对应，可能为 nullptr
```

**按特征索引 `i` 一一对应**：`mapPoints[i]` 是 `keypointsUn[i]` 对应的 3D 点。

### 为什么这个数据源是免费的

它们就是**当前帧的跟踪结果**，SLAM 每帧本来就算好了，**几百个点**。
**不需要全图快照**（那是显示 2D 地图才需要的）。

**所以「能不能测」的判断几乎零成本** —— 这是这一阶段最有利的一点。

> ⚠️ **线程**：这两者属于当前帧对象，**下一帧就变了**。
> 好在 `System` 上这两个访问器**和 `TrackMonocular` 锁同一个 `mMutexState`，而且按值返回拷贝**
> （写 `System.cc:321-323`，读 `:1327` / `:1333`）—— 所以**任意线程都能调**。
>
> **实现仍然选在 SLAM 线程上算**，但不是被迫：数据刚出炉、不用自己维护快照，
> 而且地图重置只发生在 `TrackMonocular` **内部**，同线程读不存在并发。
>
> **`MapPoint*` 也不会悬空** —— `Map::clear()` 里那两行 `delete *sit` **被上游注释掉了**
> （`src/Map.cc`），MapPoint 从不释放。最坏情况只是 `isBad()`。仍然取到就用完，别跨帧存。

## 2. 交互：十字 + 标记点

### 2.1 十字固定在**画面中心**

```
        ┌─────────────────┐
        │                 │
        │        ┼ 2.31 m │   ← 十字在中心，读数在它旁边
        │                 │
        │   [ 添加标记点 ] │
        └─────────────────┘
```

**固定**是关键 —— 所以它对应的图像坐标是**恒定的**（见 §3），不需要反向映射，
也不会有"手指挡住目标"的问题。

### 2.2 实时读数：这就是 (a)，**零操作**

十字指哪，就把那一点的三维位置算出来，**距离显示在十字旁边**。
**不需要按任何按钮。**

这就是"随身尺子"的直觉 —— 举起来有数，跟激光测距仪一样。

### 2.3 添加标记点：这就是 (b)

```
十字指到 A  →  按「添加标记点」    →  A 变成世界坐标，画面上钉住
移动手机，十字指到 B  →  按「确定」  →  显示 A-B 距离 + 画一条直线
```

**按钮文案随状态变**：还没有点的时候是 `添加标记点`，已经有一个点的时候是 `确定`。

> **未定**：**一个按钮还是两个。** 这里按一个写的，实现时看手感。

> 📌 **2026-10-11 实现时定了：一个按钮，文案恒为「加点」。**
> 因为做成了**折线**（可以一路加下去），文案随状态变反而绕 ——
> 「上一个点 → 十字」那段用**虚线橡皮筋**表示「还没定」，比改按钮文案直观。
> 同排还有「撤销」「重置」。绑定在**测距开关**上（开着才出现）。

### 2.4 核心：点一旦确定，就变成**世界坐标**

```cpp
MeasureSession { points: List<Vector3f> }   // 世界坐标，不是像素
```

用户按下去的那一刻，把那个像素对应的 **3D 点**算出来，存**世界坐标**。

**之后无论手机怎么动，那个点都钉在原地。** 移动时把它**反投影回画面**画成叠加层
——转手机时标记跟着场景走，这是"它真的在世界里"的视觉证据。

**这也让 (b) 成立**：第一个点移出视野之后仍然存在，第二点随时可以定。

### 2.5 吸附：必做，而且**必须显示会吸到哪**

十字的瞄准精度有限（转动手机很难微调），**吸附到最近的地图点**把它压到 1~2 px。
这正是 [MAP_FEATURE_IDEAS](MAP_FEATURE_IDEAS.md) §6 说的「人工指示 + 算法吸附」。

**但光吸附不够** —— 十字指着一个地方、系统却吸到了旁边一个点，而你不知道。
**所以要在画面上把吸附目标高亮出来**（一个小圈），否则按「确定」之前你不知道会定到哪。

> 吸附半径：归一化距离 **0.02**（≈ 视场角的 2%）。没吸到就退到路径 2（§4）。
>
> **实现用 `0.02 × 图像宽度` 代替**（640 → 12.8 px）。归一化换成像素本该乘 `fx`，
> 而 `System` 没暴露内参 —— `w` 是现成的，而且这样是分辨率成比例的。
> 本机 fx≈435，所以实际比设计值宽了约 1.5 倍；反正它是手感参数。

**「吸附到已有标记点」是另一回事**，也有用：量完一条边想从同一个角量另一条边时，
不用重新瞄准。**它给的是方便，不是精度。**

> **✅ 已实现（2026-10-11）。** 判据是**当帧投影的像素距离**（20 px）——
> 因为用户是按**屏幕上看到的**判断「是不是同一个角」的，世界距离阈值在不同景深下含义完全不同。
> 命中就**直接复用那个点的世界坐标**（精确闭合），不是新建一个几乎重合的点。

### 2.6 几个影响手感的细节

| 细节 | 为什么 | 状态 |
|---|---|---|
| **读数要做平滑**（最近 N 帧的中值） | 否则数字跳得看不清 | ✅ |
| **第一点移出视野时，在屏幕边缘给指示** | 量大东西时必然发生 | **未做** |
| **撤销** | 量东西经常要点三四次才对准 | ✅ |
| **清空** | 量完一次立刻再来一次 | ✅ |

> 📌 **2026-10-11**：现在移出视野的点是**直接不画**（连带那一段折线一起消失，数字还在）。
> 边缘指示留到 UI 大改那轮 —— 那时预览的黑边（现在上下各浪费约 330 px）也要一起重排。

### 2.7 可测性：**不能沉默**

| 情况 | 显示 |
|---|---|
| 十字附近有活的地图点 | **直接出数字** |
| 附近点很少 | 出数字，但标"勉强"（黄） |
| **附近没有点** | **必须给一句话**：「对准有纹理的地方」 |

> ⚠️ **沉默和"测不了"要能区分。** 如果十字指向白墙时什么都不显示，用户不知道是
> "测不了"还是"还没算出来"。

**真实限制要写进 UI 文案**：白墙、玻璃、金属、**纯色塑料**上可能一个地图点都没有。
绕法是**点边缘和角**（边缘有对比度）——而这恰好是量尺寸时本来就要点的地方。

## 3. 十字对应的图像坐标

**因为十字固定在画面中心，这一节比原方案简单得多。**

| 层 | 情况 |
|---|---|
| **letterbox 缩放** | 预览按比例居中，**屏幕中心就是图像中心** ✓ |
| **顺时针 90° 旋转** | 旋转不改变中心 ✓ |
| **畸变** | ⚠️ **仍然有一层耦合**，见下 |

**所以十字永远对应图像的 `(W/2, H/2)` = (320, 240)**，不需要通用的反向映射。

> ⭐ **这条的收益比"省一个反向映射"大得多 —— 它决定了整个实现的形状。**
>
> 十字的图像坐标**恒定** ⟹ 「测哪儿」**不是运行时参数** ⟹
> **测量可以在 SLAM 线程上每帧顺手算一次，把结果发布成一个标量，UI 只读。**
>
> **零额外 JNI 调用、零锁竞争、零 UI 往返。** 平滑也顺理成章（环形缓冲只活在 SLAM 线程上）。
> 开销实测估算 **15~25 µs/帧**，对比单帧跟踪的 26 ms ⟹ **0.1% 量级**。

> 但**预览显示的是传感器原始图像（带畸变），而 `mvKeysUn` 是去畸变之后的坐标**。
> 当前 `k1/k2/p1/p2` 全是 0（[为什么](STAGE4_CALIBRATION.md)），所以去畸变是恒等，
> 两者一致。**但这是隐藏耦合** —— 一旦标定出非零的畸变系数，它们就不再同一个坐标系了。
>
> **现在就要把这条路留对**，否则将来标定完会突然测不准，而且很难往这儿想。
>
> **第一版收口在 `centerPx(w, h)` 这一个函数里**（`measure_center.cpp`）——
> 现在它只返回 `(w/2, h/2)`。**将来只有那一处要改**：把中心过一遍畸变模型。
>
> （中心点的径向畸变最小，所以这层耦合在十字方案下的影响比点选方案**更小** —— 但不要因此不管它。）

## 4. 三条测距路径

| 路径 | 状态 |
|---|---|
| 1 最近的 MapPoint | **✅ 已实现** |
| 2 局部平面拟合 | **✅ 已实现**（形式和下面写的不同，见 §4.1） |
| 3 描述子三角化 | 未做 —— **先看路径 1+2 的实测命中率再定** |

一次取点，三条路依次尝试，谁先成功用谁：

```cpp
bool measure(const MeasureSession& s, const cv::Point2f& centerPx,
             cv::Point3f& outPoint, MeasureMethod& method)
{
    cv::Point2f q = toNormalized(centerPx, K_track_, distCoeff_);

    if (nearestMapPoint(s, q, /*radius=*/0.02f, outPoint)) { method = Method::MapPoint;    return true; }
    if (localPlaneIntersect(s, q, outPoint))                { method = Method::Plane;       return true; }
    if (descriptorTriangulate(s, q, outPoint))              { method = Method::Triangulate; return true; }

    return false;   // 明确告诉用户"此处无法测量"
}
```

### 路径 1：最近的 MapPoint（主力）

在归一化坐标里找离十字最近的、还活着的 MapPoint。**命中率约 40%，零额外计算。**

**它有一个人事不知的好处**：地图点是 SLAM **用多个关键帧三角化好**的结果，
不是在这一帧上现场三角化的。**所以「两点离得近、视差不足」这个问题在路径 1 下
不存在** —— 而 (b) 最容易踩的正是这个坑。

### 路径 2：局部平面拟合

取锥形邻域（归一化距离 < 0.15）内的 MapPoints，RANSAC 拟合平面，射线与平面求交。
**对地板、桌面、墙面效果好，覆盖率再 +25%** —— 而这三类恰好是最常量的东西。

**要注意**：拟合出的是**局部**平面。如果附近同时有地面和墙，RANSAC 可能拟合出
两者的混合平面 —— 用内点比例做一次质量检查。

### 路径 3：描述子三角化

在十字附近提取 ORB 描述子，和历史关键帧匹配，三角化出三维点。

**这条要访问历史关键帧的 `mvKeysUn` / `mvDescriptors`**，需要改一下 ORB-SLAM3
（在 `System` 里加接口），或者自己维护一份描述子缓存。

**建议最后做。** 前两条已覆盖大部分场景，这条是补边角，而它引入的
「改上游 + 自己维护缓存」两笔债不便宜。

### 4.1 ⭐ 路径 2 的实现**不需要内参**（和上面写的不同）

上面那条「射线与平面求交」要 `K`。但 **`Tracking::mK` 是 `protected`（`Tracking.h:290`），
`System` 拿不到** —— 走那条路就得改上游。

**有个等价的、免内参的形式。** 相机坐标系里的一个平面：

```
n·X = d,   X = Z·(x, y, 1),   x = (u-cx)/fx,  y = (v-cy)/fy
⟹ 1/Z = a·u + b·v + c        ← 在**像素坐标**上是仿射的
```

内参和平面参数**全被 a/b/c 吸收了**，所以直接对 `1/Z` 做最小二乘、再在十字处取值即可。
拿到的正是「沿光轴的深度」。**上游一个字都不用改。**

用**相对残差剔除 + 重新拟合**代替 RANSAC —— 确定性的，而且邻域里同时有地板和桌子时，
第一遍能把「另一张面」暴露出来。

**代价**：这条路径**给不出世界坐标**（沿光轴只知道深度，要变成点得知道归一化方向）。
所以 §2.3 那个 (b) 两点距离要做的话，得先加一个 `System::GetK()`。

> 📌 **2026-10-11：上面这两句都不成立，已修。**
> ① **世界坐标能给，而且不需要内参** —— 十字恒等于主点，那条视线在相机系里恰好是 `(0,0,1)`，
> 所以 `pw = Rcwᵀ·(0,0,z) + cam`。**⚠️ 这依赖 `cx,cy == 画面中心`，和 `centerPx()` 同一个假设。**
> ② **`System::GetK()` 也不需要** —— 投影要的内参从 `Settings` 的公开接口读得到
> （`Settings(path, sensor)` → `camera1()` → `getParameter(0..3)`），**零上游补丁**。
>
> ①这条重要：不做的话「加点」只在**路径 1 命中**时才能成功，而路径 2 恰恰是它落空时的兜底
> ⟹ **「按了按钮却没反应」会经常发生**。

### 4.2 ⚠️ 真机排查已经走过的路（2026-10-08）

> **要调参数就翻 [MEASUREMENT_TUNING.md](MEASUREMENT_TUNING.md)** ——
> 那里把每个阈值、调大调小的后果、以及「调参时看不到什么」都列成表了。

**第一版做完之后真机上的问题是「读数跳变」。跑了三轮实验，结论如下。**
细节、数据和三次自我推翻的过程全在
[changes/2026-10-08-measurement-jitter-investigation.md](../changes/2026-10-08-measurement-jitter-investigation.md)。

**根因**：每帧独立地取半径内最近的地图点，而**「这一帧哪个点被匹配上」是逐帧波动的**
（`Tracking.cc:2229` / `:2266` 把 `mvpMapPoints[i]` 置 `NULL`）。
实测：**手机没动也没转，读数在同一条视线上的 1.95 m 和 4.73 m 之间来回换。**

**⭐ 被验证有效的**（下次直接用）

| | |
|---|---|
| **目标身份锁定** | 跨帧记住那个 `MapPoint*`。**成立条件不要求它这一帧被匹配** —— 世界坐标不变，`θ` 不需要内参就能算。这一条同时吃掉了 34% 的「目标丢失」 |
| **释放阈值要比吸附宽** | 滞回必须「释放比获取宽」。取一样宽的话，半径边缘选中的点下一帧就锁不住 |
| **`θ` 判据** | `θ = atan2(‖pc.x, pc.y‖, pc.z)`，**不需要内参** |

**⚠️ 被真机数据推翻的**（别再试）

| 别再试 | 为什么 |
|---|---|
| **按深度取「最近的那一层」** | 看着像在实现遮挡先验，实际**专门挑中三角化错的坏点** —— 稀疏地图里的坏点恰恰长成「几乎在光轴上、深度却很小」的样子。实测那些跳变的读数**全落在吸附半径的边缘（11.6 px / 12.8 px）**，而稳定读数在离中心 2~5 px |
| **「让位」规则**（出现更近的点就切） | 同源。它只触发一次，而那次让位给的是坏点 |
| **获取去抖** | 按身份或按深度都一样：**丢失率从 20% 涨到 39%**，没有可见收益 |
| **把中值窗口调大** | **错的工具**。窗口压的是**毫米级**的位姿噪声，压不了**米级**的层间换人 —— 「一半样本在 A 层、一半在 B 层」这种双峰输入，中值只能输出 A 或 B |

**还没解决的**

- **「坏地图点」没有识别手段。** 只证明了「按深度挑会挑中它们」，**没做到把它们剔掉**。
  可疑信号：被观测次数少、三角化基线短、孤立。`MapPoint` 上有
  `mnFound` / `mnVisible` / `GetObservations()` —— **一条都还没查**。
- **「目标丢失」没拆开**：是「这一帧没匹配」还是「被剔成外点」。

**⚠️ 一条会骗人的字段**：诊断用的 `跨度`（半径内候选的深度最大相对跨度）
**只统计这一帧被匹配上的点** —— 所以「两次都是 `候选1 跨度0%`」也可能相距 2.8 m。
**别只看它下结论。**

### 4.3 没走的路：稠密化

路径 1+2 的覆盖上限由**地图点的密度**定死。想突破就得**把稀疏变成稠密**。查过的候选：

| 路线 | 覆盖 | 精度 @1.6 m | 手机实时 | 结论 |
|---|---|---|---|---|
| **单目米制深度网络**<br>（Metric3D v2 / Depth Anything V2 Metric / UniDepth） | 100% | ❌ **MAE ≈ 2.6 m 量级**，而且**近处最差**、8–12 m 才勉强能看 | ❌ **515 ms ~ 2.4 s/帧** | 精度差**两个数量级**、速度差**一到两个数量级**。训在 KITTI/驾驶场景上，**室内 0.5–3 m 是分布外** |
| **稀疏深度补全**<br>（LingBot-Depth-*DC* / IU-DC / OMNI-DC） | ~100% | 理论最优（用我们的稀疏点做锚） | ❌ ViT-Large ~300M，**没有端侧先例** | 方向对，但全是研究代码、KITTI/LiDAR 训练。**它是第二批的候选** |
| 立体 / MVS | 高 | 好（有基线时） | ❌ | 单目 + 手部微动，基线太小 |
| **参照物换算**（A4 纸、硬币、已知尺寸的砖） | 100% | **最好**，可以比 SLAM 准 | 交互麻烦 | **不实现，记成「精度兜底」** |

> ⭐ **深度补全那条路的输入正是「RGB + 稀疏米制深度图」**，而那个稀疏深度图
> = 我们每帧的 `mvpMapPoints` 投影回图像。**路径 1+2 做出来的东西本来就是它的前置**，
> 将来接得上，不用推翻。

**顺带回答「别的应用怎么做的」**：不用 ARCore、没有深度传感器的 Android 测距 app
（**ImageMeter**、**Camera_Measure**），做的**不是三维重建，是参照物换算** ——
因为单张照片在数学上就恢复不出绝对尺度。有 ARCore 的（Google Measure、AR Ruler）
靠平面 hit-test，也就是**等价于路径 2**。

**我们这个方案比它们强的地方**：真的有一张米制尺度的三维地图，缺的只是稠密性。

## 5. 融合与置信度

> ⏳ **未实现。** 第一版只有**顺序兜底**（路径 1 落空才跑路径 2），不做多路径融合。
> 头文件里留了 `method` 字段，等有实测数据了再看要不要加。

一次取点可能有多条路径给出结果。**取中值，不要取均值**（对误匹配鲁棒）：

```cpp
cv::Point3f fused;
if (!medianOf(results, fused)) return MeasureResult::Failed;

float spread = maxDeviation(results, fused);
if (spread > 0.05f) return MeasureResult::LowConfidence;
```

| 结果 | 提示 |
|---|---|
| 多条路径一致（离散度 < 2cm） | 正常显示距离 |
| 路径间离散度大 | 「测量结果不确定，请靠近目标或对准有纹理的表面」 |
| 全部失败 | 「此处无法测量」 |

**这是本阶段的价值观，不是可选装饰。** 一个会说"我不知道"的工具，
比一个总是给数字的工具可信得多。

## 6. 精度与不确定度

误差主导项是**位姿误差**，`σ_z ≈ z·δθ`，ORB-SLAM3 Mono-Inertial 典型 1% 量级：

| 距离 | 典型误差 |
|---|---|
| 1 m | ~1 cm |
| 3 m | ~3 cm |
| 8 m | ~10 cm+ |

**本项目的实测校正**：尺度验证给出「轨迹米制尺度 ≈ 0 ± 2%，无系统性偏差证据」，
单对测量散布 ±3~4pp（≈5~6cm @1.6m）。按「**cm 级 / 相对 2~5%**」规划。

> ⚠️ **只报点选误差和融合离散度，会给出虚假的自信。** ±2% 的尺度误差是
> **系统性的**，不会因为多测几次而平均掉。**UI 至少要给一个粗略的误差范围。**

**「用参照物校正」是可选，不是必须** —— 定位是"粗糙好用的随身尺子"，
±2% 在 1 m 上 2 cm，对"这柜子大概多长"完全够。

## 7. 时效性：结果会过期

回环优化会**改写历史位姿**，之前测出的距离可能不再成立。信号是现成的：

```cpp
bool MapChanged();     // 地图刚被回环 / 合并大改过
```

**测到 `true` 时提示**「地图刚被优化，之前的测量可能需要重算」。

**测量结果不保存**（2026-09-26 定），所以不需要考虑"存下来的结果怎么跟着地图更新"。

**返回主界面时测量会话保留**（量到一半去看地图，回来点还在）。
