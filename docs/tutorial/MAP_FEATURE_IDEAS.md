## 一、三个设想

| # | 设想 | 一句话 |
|---|---|---|
| 1 | **迷宫路线记录** | 走进去，记下走过的路，能原路返回 |
| 2 | **随身尺寸测量** | 不用带工具，手机掏出来量个大概 |
| 3 | **SLAM 可观测性**（地基） | 让「现在行不行」变成看得见的东西 |

**第 3 条不是第三个功能，是前两条的共同前置。**

最初还有两个设想，一个被剔除、一个被降级：

| 原来的 | 处置 | 为什么 |
|---|---|---|
| AR 导航 | **剔除** | 难点不在渲染，在**路径规划**（稀疏点云不构成可通行空间），是唯一需要新算法的部分 |
| 室内定位 / 停车场找车 | **降级为「路线记录」** | 见第五节——这是一次重要的收敛 |

## 二、共同前提

| 前提 | 为什么 | 现状 |
|---|---|---|
| 实时 SLAM 在手机上跑通 | 都要实时位姿和实时地图 | 阶段五进行中 |
| **能拿到地图内容的接口** | `System` **没暴露地图**（`mpAtlas` 是 private），也**没有** `GetAllKeyFrames()` / `GetAllMapPoints()`——得自己加 | 未做 |
| **深拷贝的快照机制** | `Map::GetAllKeyFrames()` **本身有锁**，但锁只在把指针拷进 `vector` 那一瞬间持有；**出了函数你手上是一堆裸指针** | 未做 |
| 坐标变换辅助代码 | 世界系 → 相机系 → 像素 | 未做 |

> ⚠️ **别把「快照」那条理解成「加个锁就行」。** `Map.cc:149` 已经加了
> `unique_lock<mutex> lock(mMutexMap)`。真正的纪律是**快照在 SLAM 线程上取、
> 并且深拷贝出来，UI 线程永远不碰 ORB-SLAM3 的指针**——加锁解决不了
> 「锁释放之后指针被改」。

## 三、贯穿事实之一：地图是**稀疏**的

ORB-SLAM3 的地图是 **MapPoint + KeyFrame**，不是点云、不是网格：

- `MapPoint`：一个 3D 点 + 描述子 + 被哪些关键帧观测到
- `KeyFrame`：位姿 + 该帧全部特征点的描述子 + 它看到的地图点

典型规模：**几百到几万个离散 3D 点**。没有面、没有体、没有「自由空间」的概念。

**三条设想的所有难点，几乎都源自这一条。**

一个具体推论：**白墙、玻璃、金属、纯色塑料上可能一个地图点都没有。** 想在上面量东西，
得**点边缘和角**（边缘有对比度）。

## 四、贯穿事实之二：地图持久化

### 能存能读，机制是通的

`System::SaveAtlas()` / `LoadAtlas()`，输出 `<名字>.osa`。`System::Shutdown()`
**会自动存一次**（System.cc:547，`BINARY_FILE` 格式），
只要 yaml 里 `System.SaveAtlasToFile` 非空。

加载时旧图的关键帧**会被重新灌进 `KeyFrameDatabase`**：

```
System::LoadAtlas()
  ├─ :1499  mpAtlas->SetKeyFrameDababase(mpKeyFrameDatabase)
  └─ :1501  mpAtlas->PostLoad()
              └─ Atlas::PostLoad()                              Atlas.cc:335
                  └─ :348  pMi->PostLoad(mpKeyFrameDB, mpORBVocabulary, mpCams)
                            └─ Map::PostLoad()                  Map.cc:427
                                └─ :469  pKFDB->add(pKFi)       ← 重新注册
```

**所以重定位查得到旧图**——`Relocalization()` 查的就是这个 DB。

### 四个坑

| 坑 | 具体 | 性质 |
|---|---|---|
| **路径写死在 `./`** | `System.cc:1411` / `:1450` 都是 `string path = "./"` 再拼文件名。Android 上进程 CWD 是 `/`，**不可写** | **必改**，几十行内 |
| **Boost 是硬依赖** | `ldd` 证实 `libORB_SLAM3.so` 链着 `libboost_serialization`；13 个文件的 `serialize()` 没有 `#ifdef` 保护。**哪怕不存地图也要链接它** | Android 上要自己编，见 [STAGE5 §3.4](STAGE5_JNI_BRIDGE.md#34-boost-是硬依赖而-android-上得自己编) |
| **绑定词袋** | 存的时候写了词袋校验和，读的时候比对（`System.cc:1490`） | 换词袋 ⟹ 旧地图全废 |
| **`Atlas` 没有 `SetCurrentMap()`** | 只有 `CreateNewMap()` / `GetCurrentMap()` / `GetAllMaps()`；加载后立刻 `CreateNewMap()`，**当前图是空的新图，旧图躺着没人用** | **要自己加**，见 [APP_DESIGN](APP_DESIGN.md) |

### 它**不**省时间

**「载入旧图会更快」是错的**，三条都躲不掉：

1. `LoadAtlas` 之后仍然 `loadFromTextFile(ORBvoc.txt)`（139 MB 文本）——
   atlas 里**只存校验和，不含词袋**
2. 惯性初始化照样要做（IMU 每次上电的 bias 都不同）
3. 还**多了一步**读文件

**所以别写「延迟加载」那套** —— 省不下大头。

### 已有地图的价值是「资产」，不是「快」

位姿相对**同一张图**，两次会话的坐标可比、可累积；地图本身成为资产。
这个 reframe 重要：如果动机是"快"，这条路该降优先级；如果是"资产"，它是
想法一的地基。

### ⚠️ 待实测

**上面这一节的每一条都是读源码得到的，但 `LoadAtlas` 这条路一次都没跑过。**
有一件事读代码读不出来：**加载之后要不要重做惯性初始化**。

- `mbImuInitialized` 确实被 `Map::serialize` 保存（旧图带着"我已初始化"的标志）
- **但加载后紧接着 `CreateNewMap()`，当前图是一张空的新图**（它的标志是 false）

所以实际行为取决于追踪之后怎么切图，**这块是 ORB-SLAM3 最糙的部分**。

**该做的实验**（成本很低，而且它同时决定「继续上次」这条路可不可行）：

```
建图 → SaveAtlas → 重启 → LoadAtlas
  ① 打印 Atlas::GetAllMaps().size() 和 GetCurrentMap()->GetAllKeyFrames().size()
       期望：≥1 张旧图（有关键帧），当前图 0 个
  ② 跟丢，看能不能重定位到旧图
       期望：不能——候选被 pMap 过滤挡住（见「四个坑」最后一条）
  ③ 自己加 SetCurrentMap(旧图) 再试
       这一步是这条路能不能走的试金石
```

**①② 零风险**（只加打印），建议先做它们，**别直接改 `Tracking`**。

## 五、设想一：迷宫路线记录

> **目标：走进去，知道怎么出来。**

### 为什么「路线记录」比「室内定位」好得多

原来写的是「室内定位 / 停车场找车」。**降级成路线记录是一次重要的收敛**：

| 需要什么 | 室内定位 | 路线记录 |
|---|---|---|
| 重定位 | 必需 | **不需要** |
| 地图复用 | 必需 | **不需要** |
| 绝对精度 | 要（否则找不到车） | **不要**，只要**相对形状对** |
| 尺度误差 ±2% | 有影响 | **无所谓** |

**全部落在「零框架改动」那一批里**，而「原路返回」这个用途，轨迹画出来就完成了。

### 重力对齐是白送的 ⭐

因为用的是 **Mono-Inertial**，地图在惯性初始化完成时会被**整体旋到重力对齐、
并施加米制尺度**（LocalMapping.cc:1282）：

```cpp
Sophus::SE3f Twg(mRwg.cast<float>().transpose(), Eigen::Vector3f::Zero());
mpAtlas->GetCurrentMap()->ApplyScaledRotation(Twg, mScale, true);
```

于是：

- **世界坐标系的 Z 轴就是竖直方向** → 「水平面」= **XY 平面**，不用自己估
- **单位是米** → 「高度」直接读 z 坐标

纯单目这两样都得自己求。**这是 Mono-Inertial 白送的好处，而且它就是「2D 地图投影」
的前提** —— 投影到 XY 平面即可。用之前要知道它从哪来。

### 真瓶颈是**弱纹理**，不是尺度

迷宫、走廊如果墙面单调（白墙、水泥），ORB 提不出特征 → **跟踪直接丢**。

**这是做之前要先验的那件事**，它决定这个功能在具体场景里成不成立。

### 实现：从「轨迹图」起步，不做「栅格地图」

| 做法 | 工程量 | 效果 |
|---|---|---|
| **关键帧位置连成线（轨迹图）** | **极小** | 信息量低，但立刻可用，零新算法 |
| 地图点栅格化 + 膨胀 | 中 | 像平面图，但仍有大量空洞 |
| 建占据栅格 + 通道拓扑 | 大 | 导航能用，但这已经是新算法 |

**先做轨迹图版本**：它验证整条链路（读地图 → 变换 → 渲染），但不引入任何新算法。

### 多传感器：备选，不是必需

原来这条是「绕开感知混淆的路」。**降级成路线记录之后，感知混淆不再是主要矛盾**，
所以它从"架构的一部分"降为**备选**。

但它的信息仍然有效（而且都不依赖 GMS，符合项目约束）：

| 信号 | API | 精度 | 备注 |
|---|---|---|---|
| WiFi 指纹 | `WifiManager` | 几米 | 室内通常有 AP |
| BLE beacon | `BluetoothLeScanner` | 1~3 米 | 自用可自己布 beacon |
| 气压计 | `Sensor.TYPE_PRESSURE` | 楼层级 | 需先确认机型有没有 |

> ⚠️ **前两行的代价不是代码，是权限。** Android 上 `WifiManager` 拿扫描结果需要
> **定位权限**（且系统位置服务要开着）；`BluetoothLeScanner` 在 API 31+ 需要
> `BLUETOOTH_SCAN`，而且真要拿它推位置就不能声明 `neverForLocation`。
> 「顺手加个信号」实际上是「要一个权限」，排期时要算进去。

## 六、设想二：随身尺寸测量

> **目标：不用带工具，手机掏出来量个大概。**

### 价值边界（诚实版）

| | 赢 | 输 |
|---|---|---|
| 精度 | — | 激光测距仪 ±1.5 mm、60 块，**碾压** |
| **手边有没有** | ✅ 不用带工具 | — |
| **单人操作** | ✅ 高处、大件、够不着的东西 | — |

**定位是「粗糙好用的随身尺子」，不是「替代激光测距仪」。** 这个定位决定了精度目标：
**cm 级就够**，不需要 mm 级。

（历史备注：曾经把「卡边判断，家具能不能进门」当作核心价值，**那是错的，已删**。）

### 两种测量，难度差一个量级

| | (a) 到目标的距离 | (b) 两点之间的距离 |
|---|---|---|
| 需要几个点 | **1 个** | 2 个 |
| 误差 | **单点深度误差** | **两个点误差叠加** |
| 实测散布 | — | ±3~4pp（≈5~6cm @1.6m） |
| 像什么 | **激光测距仪** | 卷尺 |

**(a) 是低垂的果实**：不需要移动手机、不需要第二个点、精度更高。**先做 (a)**，
(b) 用同一套交互自然延伸——点一个点给 (a)，再点一个给 (b)，**不需要选模式**。

### 一个有利的技术性质

如果两个点都**吸附到已有的地图点**，那么它们的 3D 位置是 SLAM **用多个关键帧
三角化好的结果**，不是在这一帧上现场三角化的。

**所以「两点离得近、视差不足」这个担心在「吸附」前提下不存在。** 那条教训
（09-23：远端标记视差仅 11°）说的是**现场三角化**。

**推论：吸附成功率 = 可测率，而地图点密度决定一切。**

### 精度预算

| 误差源 | 性质 | 量级 |
|---|---|---|
| 位姿误差 `σ_z ≈ z·δθ` | 随机 | 1 m 约 1 cm、3 m 约 3 cm |
| 尺度误差 | **系统性** | ±2%（阶段四实测） |
| 点选误差 | 随机 | 手指 ±20 px；**吸附后 1~2 px** |
| 三角化深度误差 | 随机 | ∝ z² / 基线 |
| 多路径融合离散度 | 随机 | 见实现设计 |

### 不确定度：不能只报随机项

> ⚠️ **只报告随机误差，会给出虚假的自信 —— 比不显示更坏。**

±2% 的尺度误差意味着量 1 m 的东西偏 2 cm，**它是系统性的，不会因为多测几次而平均掉**。
如果 UI 只报点选误差和融合离散度，用户会看到一个很小的数字，而真实误差被尺度项主导。

**但「用参照物校正」降级为可选** —— 因为定位是「粗糙好用」而不是「卡边判断」，
±2% 在 1 m 上 2 cm，对"这柜子大概多长"完全够。

**保留的是「显示一个粗略的误差范围」这条原则**，不是校正本身。

### 人工指示 vs 语义分割

结论：**都不是，应该是「人工指示 + 算法吸附」。**

语义分割解决的**不是瓶颈**：识别不是难点，**3D 几何才是**。

1. **遮挡** —— 只看到一个面的箱子，算不出它有多深。**这是本质问题，不是精度问题。**
2. **稀疏深度** —— mask 里绝大部分像素**没有地图点**
3. 「尺寸」的定义本身就模糊（含不含扶手、含不含靠背）

**人的识别能力是免费的、极强的、零算力的。** 随手一点就知道要点箱子的哪两个角。

人工指示唯一的短板是手指 **±20 px**，吸附到地图点就能补掉，**成本极低**。

### 实现顺序

```
第一版：点选 + 吸附到地图点 → 到目标的距离 (a)
第二版：两点距离 (b)、多点（对角线、面积）
第三版：交互式分割，吸附到轮廓
```

语义分割**排在最后**：在几何问题（遮挡、稀疏深度）解决之前，
**它不会让功能变得更可用**。

## 七、设想三（地基）：SLAM 可观测性

### 它针对的是这个项目真正的历史痛点

- 采了 20 秒 → 全废，但**当时不知道**，拿回 PC 跑完才发现
- 重采 65 秒 → 好了，但 **1/3 概率仍然失败**，同样是事后才知道
- 花了好几轮**从日志里反推** `mTinit`、VIBA2、重置路径

**全部指向同一件事：SLAM 是个黑盒，你不知道现在行不行。**

**而「测不准」从来不是主要问题 —— 「不知道现在能不能用」才是。**

### 现成的信号（不用改上游）

| 指标 | API |
|---|---|
| 跟踪状态 | `GetTrackingState()` + `isLost()` |
| 初始化完没完 | `GetTimeFromIMUInit()` |
| 地图刚被大改过 | `MapChanged()` |

两个关于 `GetTimeFromIMUInit()` 的细节：

- **它是「二值 + 时长」，不是进度条**：初始化完成前恒返回 `0`，完成后返回
  「距首帧多久」。**拿不到"完成到百分之几"** —— 所以别做进度条，做不确定的动画。
  （这条和 [STAGE7](STAGE7_UI_STATE_MACHINE.md) 里那条是同一件事。）
- **`MapChanged()` 直接服务测量**：它就是「地图刚被回环优化改过」的信号，
  测量结果的时效性提示要靠它。

### 要自己算的：覆盖率

关键帧位置 + 朝向 + FOV 累积。**要自己加接口拿地图。**

### 形态必须分时刻，不能是同一个 UI

> ⚠️ **建图时用户端着手机走动，根本没法盯屏幕。**

所以「实时热力图」这个形态是错的。三种粒度：

| 时刻 | 用户在哪 | 该显示什么 |
|---|---|---|
| **建图时** | 走动中，瞥一眼 | 极简：够不够开始测的二值 |
| **建图后、测量前** | 停下看屏幕 | 画缺口："哪面墙还没覆盖" |
| **点击测量时** | 盯着预览 | **可测性**，不是覆盖率 |

**「建图完毕再提示可以测量」是错的判据** —— 全局覆盖率说明不了局部：

- 覆盖 80%，但你要量的那个角落没点 → **照样测不了**
- 覆盖 30%，但正对着刚扫过的桌子 → **照样能测**

**正确的反馈是局部的「此处可测 / 不可测」。**

### 「未扫描」的定义必须诚实

ORB-SLAM3 里**没有**「未探索区域」这个概念，得自己构造：

| 做法 | 问题 |
|---|---|
| **关键帧视野扇形**（位置 + 朝向 + FOV 累积） | 最简单最诚实。不做遮挡推断，墙后的区域也会被标成"看过" |
| 视野锥 + 射线遮挡 | 稀疏点做遮挡极其粗糙，点与点之间全是"透明" |
| 特征点密度热力图 | **分不清「没去过」和「去了但没纹理」** |

**从第一种起步** —— 它**不假装知道墙在哪**，只显示"我在哪些位置朝哪些方向看过"，
这个信息**准确**。**准确比好看重要。**

## 八、建议顺序

```
第一批（零框架改动、零新算法）
  可观测性            ← 直击历史痛点，是另两条的共同前置
  迷宫路线记录        ← 只要轨迹显示
  随身测量（先做 a）   ← 吸附 + 可测性反馈

第二批（改框架，成本已因「手动重定位」大幅降低）
  存 / 载地图 · 切图 · 路径点 · 重定位
```

**理由**：第一批**不碰 ORB-SLAM3 内部**，能独立验证、独立产生价值，
而且它们会积累出「地图该多大、够不够用」的判断。**第二批的收益依赖那些判断**——
现在做等于盲猜。

**风险提示**：地基那条**不产生直接的最终价值**（用户要的是量尺寸或找路，
覆盖率是手段）。这是所有基础设施类功能的共同特征，接受它。
