# 内参会不会随对焦距离变？

> **状态：未定论的假设 + 调研。** 2026-09-28。
>
> 起因是一个观察，查下来发现它牵出两件事：一个是**代码里已经埋下的隐患**，
> 一个是**两个互相竞争的假设**。判别实验还没做。
>
> 本文记录假设、证据、文献做法和待办的实验，不是结论。

---

## 一、问题从哪来

用户注意到一个不一致：

- **拍标定板时**，板子在屏幕上，对焦在**最近**处
- **测量时**，对焦在**地板 / 远处物体**上

于是合理的怀疑：**标定标出来的 `fx` 未必适用于测量。**

---

## 二、代码里已经埋了一个更大的隐患

`CameraCapture.kt` 的对焦回调有**两条分支**，fx 的行为完全不同
（CameraCapture.kt:379-388）：

| 分支 | 条件 | fx 的行为 |
|---|---|---|
| **锁死** | 读到了有效的对焦距离 | 整个会话 fx **固定**，但固定在"按下「准备」时瞄着的那个距离" |
| **连续对焦** | 读不到（`dist == null \|\| dist <= 0`） | **fx 在会话中随拍摄距离漂移** |

> 代码注释自己写了这个代价：「代价只是焦距会随拍摄距离轻微呼吸」。

**而 `meta.json` 不记录用了哪条分支、锁在多少屈光度** —— 那句
`Log.i("镜组锁定于 %.3f 屈光度")` 只进了 logcat，**没落盘**。

**所以现在无法回溯任何一次采集锁在哪。** 这是本文大多数问题查不下去的直接原因。

---

## 三、已确认的现象

三次 ChArUco 标定给出的 fx：**435.2 / 439.2 / 452.3**（跨录制 **3.9%**）。

同时已知：**组内子集重标是稳定的**（`cx` 只差 ±0.7 px、`fx` ±2%）。

**即：变异发生在「会话之间」，不在「会话之内」。** 这与对焦假设的形式吻合 ——
对焦距离是每次采集各自锁定的，天然是"会话间"的量。

---

## 四、两个竞争假设

| 假设 | 机制 | 解法 |
|---|---|---|
| **A. 对焦呼吸** | 镜组位置不同 → 有效焦距不同 | 建表 + 插值（见 §六） |
| **B. 畸变与 fx 耦合** | 角点覆盖不足 → `k1`/`k2` 没被约束住 → 误差被吸收进 fx | 补四角覆盖（本来就欠这一条） |

**B 不能排除**：标定时画面四角的覆盖只有 **2.0 / 4.3 / 3.6 / 7.3%**（门槛 5%），
重标时 `k2` 连符号都会翻 —— 说明它根本没被数据约束住。**没约束住的畸变会把误差挤进 fx。**

### 一条**削弱假设 A** 的证据（重要）

fx 裁定的那一步，用的恰恰是**测量对焦下的数据**（1.6m 杆，斜指景深），
扫描出的重投影极小值落在 **435.2** —— 和屏幕对焦下 ChArUco 给出的一致。

**如果对焦呼吸显著，这两个值不该吻合。** 所以这条证据倾向于：这台机器的对焦呼吸**不大**。

> ⚠️ **但这条证据不硬**，现在有三个原因：
> 1. 扫描的候选值只有 5 个（420 / 422.7 / 435.2 / 440 / 452.3），**粒度粗**
> 2. 这些候选值本身就是从 ChArUco 结果里挑的，**有选择偏差**
> 3. **（2026-09-30 新增）「重投影极小值」这个判据本身不稳。** 新 session 上测三对，
>    每对各自扫 fx 看重投影误差最小在哪 —— **三对指向三个不同的 fx**
>    （435.2 / 435.2 / **452.3**）。见
>    [changes/2026-09-30-scale-verification-on-new-session](../changes/2026-09-30-scale-verification-on-new-session.md) §决策五

**所以 A 和 B 都还站着**，需要 §七 的实验来分。

### 📌 2026-09-30 的新数据（尺度验证顺带得到的）

新 session（62 秒，`-O3` 修好之后第一趟能跑完的）上标了**四块地砖 × 40 cm = 1.6 m**，三对读数：

| 帧对 | 视差 | 距离(1.6 真值) | 误差 |
|---|---|---|---|
| 1271 & 1306 | 16.5° / 5.6° | 1.4829 | −7.32% |
| 1009 & 1070 | 22.5° / 8.3° | 1.5112 | −5.55% |
| 784 & 845 | 20.2° / 6.3° | **1.7226** | **+7.66%** |

**均值 −1.74%**（9-23 是 −1.6%，**吻合**），但**极差 14.98pp**（9-23 只有 ±3.7pp）——
因为这次的视差只有 5.6~8.3°（9-23 是 11~34°）。**第三对又反向**，
**再次印证「2 个样本不下结论」。**

**对本文的意义**：`fx` 和**尺度**在三角化距离里是**乘法关系，单次测量分不开**。
所以想用「量已知长度」反推 fx，**前提是尺度已经独立可信** —— 而尺度本身也有 ±2~5% 的不确定。

## 五、文献里是怎么处理的

### 这是个已被命名的问题

术语是 **dynamic intrinsics** —— 主流三维方法（NeRF、3DGS、SLAM）都假设内参在整个视频里不变，
**这个假设在手机自动对焦和单反变焦上都不成立**。

> 而且有独立工作印证了我们的观察：
> **"Repeated smartphone calibrations vary across sessions"** ——
> 手机重复标定跨会话就是会变。

### 主流解法就是**建表 + 插值**

| 方法 | 场景 | 出处 |
|---|---|---|
| **按对焦距离 1D 插值** | 定焦镜头（**本项目的情况**） | 专利 CN105118055A：用 **slerp** 插值姿态修正四元数，权重 `t = (FD_{j+1} − FD)/(FD_{j+1} − FD_j)` |
| **二维插值（焦距 × 对焦距离）** | 变焦镜头 | 同上：先在网格上按焦距插、再按对焦距离插 |
| **LUT + 双线性 / Delaunay 重心插值** | 非规则网格 | InFlux benchmark：`K(l,d) = Interpolate({(LFL_i, FD_i, K_i)})` |

### 两条必须知道的约束

1. **改变对焦不只是改内参，还可能改畸变系数。** 所以表不能只存 `fx/fy`，
   得连 `k1/k2` 一起存。（Bossemeyer 等）
2. **精确估计需要高密度的采样点。** 这不是"标两个点连条线"，是要在多个对焦距离上分别标。

### Android 的出厂标定救不了这件事

`LENS_INTRINSIC_CALIBRATION`（`[fx, fy, cx, cy, s]`）和 `LENS_DISTORTION` 确实存在，
但经查证它们是**静态的**（不随对焦变），多半是在某个固定对焦位置（通常无穷远）标定的。

**但作为独立的第三方参考值仍然有用** —— 读一次 `CameraCharacteristics`，
拿它的 fx 和 ChArUco 结果对一下，能判断我们的标定有没有系统性错误。

## 六、一条关键的可操作性发现

**`LENS_FOCUS_DISTANCE` 不只是能读，它是可以设置的。**

```kotlin
// CameraCapture.kt:483 —— 已经在这么用了
set(CaptureRequest.LENS_FOCUS_DISTANCE, focusDistance)
```

这意味着两件事：

1. **判别实验可行** —— 不需要靠"瞄目标"间接控制对焦距离，可以直接命令它
2. **建表可以自动化** —— 脚本依次命令对焦到 N 个距离、各录一段，不需要人工摆位

**这是本文最有操作价值的一条。** 没有它，§七 和 §八 都得靠手工控制，容易做不准。

## 七、判别实验（**未做**）

```
固定对焦 0.5 m → 录一段标定 → fx₁
固定对焦 2.0 m → 录一段标定 → fx₂
```

| 结果 | 结论 |
|---|---|
| `fx₁ ≈ fx₂` | 对焦呼吸不是主因 → **去补四角覆盖**（假设 B） |
| 差 > 2% | 对焦呼吸确认 → **建表值得做**（假设 A） |

**现在做不了** —— App 目前只能"从对焦点读出来再锁住"，不能指定。
需要一个 App 改动：让对焦距离可指定（§六 那条）。

> ⚠️ 每组要跑**多次**。这个系统的单次运行不可复现是已知问题
> （见 [ORB_SLAM3_TRACKING_FLOW.md](ORB_SLAM3_TRACKING_FLOW.md) §八末），
> 但标定本身是确定性的（纯图像处理），所以这里主要防的是**采集差异**。

## 八、两条路线

### A. 建表 + 插值（学术正解）

在 N 个对焦距离各标一次 → 表 `fx(d) / k1(d) / k2(d)` → 运行时用
`LENS_FOCUS_DISTANCE` 插值。

**前提**：每个采样点都要标得准。**陷阱**：如果标定本身因为覆盖不足而不稳，
表里每个点都不稳 —— **插值会把一个随机的表插成一条平滑的错误曲线**。

### B. 提高标定质量 + 已知参照当场校准（工程务实）

1. **补四角覆盖重录标定**（本来就欠这一条）
2. 加**已知参照当场校准**：测量时画面里放一个已知尺寸的东西
   （A4 纸 297 mm、银行卡 85.6 mm），让当次的 fx / 尺度偏差被吸收掉

**B 的最大优点**：它是唯一一个**不依赖"成因判断是否正确"**的方案。
不管 fx 抖动是对焦还是畸变引起的，参照物当场校准都盖得住。

### 建议的顺序

```
1. 先做 §七 的判别实验（需要 App 支持指定对焦距离）  ← ✅ 前提已满足，见 §六
2. 同时补四角覆盖重录标定 —— 无论如何都要做，且能顺带排除假设 B
3. 若确认是对焦 → 走 A（用 §六 的能力脚本化建表）
4. 无论走哪条 → 加 B 的第 2 条做兜底
```

**先做 2 的理由**：它零成本（本来就该做），而且做完之后假设 B 自动出局或坐实。

> **📌 2026-09-30：第 1 条的前提已经满足。** `CameraCapture.buildRequest()` 现在接受
> `focusDistance: Float?`，`AF_MODE_OFF` 和 `LENS_FOCUS_DISTANCE` 一起给 ——
> **判别实验和自动建表现在都能做了。**
>
> **但优先级建议往后放**（见 §十一）。理由：`fx` 与**尺度**在三角化距离里是乘法关系，
> 而尺度自己有 ±2~5% 的不确定 —— **单靠「量已知长度」反推 fx，精度被尺度吃掉**。
> 而 §八-B 的第 2 条（已知参照当场校准）**直接吸收掉两者的合成偏差**，不依赖这个判断。

## 九、顺带发现的一个边界问题

```kotlin
if (dist == null || dist <= 0f) { /* 当作"读不到"，退回连续对焦 */ }
```

**但 `0` 是合法值 —— 它表示对焦在无穷远**（`LENS_FOCUS_DISTANCE` 的单位是屈光度，
`0` = ∞）。所以对着很远的景物对焦时，`dist` 趋近 0，代码会误判成"读不到"，
退回连续对焦 —— **fx 开始漂**。

室内 1~3 m 时 `dist = 0.33 ~ 1.0`，碰不到；**室外会对上**。

> **📌 2026-09-30 复核：代码里不是漏了，是有意取舍。**
> `CameraCapture.kt:398` 的注释自己写着「读不到有效距离（**0 表示未知，或者镜组在无穷远**）」，
> 并且说明了为什么宁可退回连续对焦（切 `AF_MODE_OFF` 会让镜组停车、把画面搞糊）。
>
> **所以这条不是 bug，是「两个坏选项里挑了一个」。** 真要修，得先能把「0 = 无穷远」
> 和「0 = 读不到」分开 —— 那需要**另一个信号**（比如 `LENS_STATE` 或对焦距离的
> 可用性标志）。**本文档不再把它列为待办，降级为「已知取舍」。**

## 十一、这个什么时候做

**不是「测距」的前置条件，但会影响测距的精度。**

| | |
|---|---|
| **不影响能不能测** | 场景六的十字测距用的是 SLAM 的稀疏地图点，**fx 只影响三角化深度、不影响跑不跑得起来** |
| **影响测得准不准** | fx 差 1% → 深度差 1% → 距离差 1%（和尺度误差**同向叠加**） |
| **和尺度的不确定度叠加** | 尺度自己有 ±2~5%（9-23 与 2026-09-30 两次验证的共识） |

### 建议的顺序

1. **先做 §八-B 的第 2 条**（已知参照当场校准）—— **工程上最划算**
   它**不依赖「成因判断是否正确」**：不管 fx 抖动是对焦还是畸变引起的，
   参照物当场校准都盖得住。而且它天然吸收掉**尺度**的偏差
2. **顺手做 §八-B 的第 1 条**（补四角覆盖重录标定）—— 零成本，做完假设 B 自动出局或坐实
3. **再回头做本文 §七 的判别实验** —— 前提已满足，但它回答的是「为什么」而不是「怎么办」。
   **除非打算走 §八-A（建表 + 插值），否则它的收益有限**
4. **`phone.yaml` 合标定值** —— 独立的一步，什么时候做都行（见 §十）

### 我建议的优先级

**一句话**：**先用「已知参照当场校准」把效果兜住，再从容地查成因。**
反过来的话，会为了一个「不需要精确知道」的量耗很久 —— 而 2026-09-30 那次测量已经显示
**fx 和尺度在单次读数里分不开**。
