# 2026-10-28 跨会话把时间轴接上，避免每趟都重建地图

一句话：每趟「启动」的第一帧时间，从"真实过了多少秒"改成"接着上一趟加一帧"，
于是 ORB-SLAM3 的跳变守卫不再触发，地图不再被拆开。

## 动机

真机日志里，每一趟「启动」都出现：

```
Timestamp jump detected. State set to LOST. Reseting IMU integration...
Creation of new map with id: 1
Stored map with ID: 0
[M5] 地图被重置（第 1 次）
```

代价有三个：图 id 每趟变一次（历史轨迹按图分目录）、开头要重新初始化一遍、
最后还得等一次合并才能回到同一张图。

根因在 `slam_engine.cpp` 的 worker：时间基准 `base` 是**整个进程**的第一帧，
所以两趟之间停的 20 秒会原样出现在喂给 SLAM 的时间戳里。而
`Tracking.cc:1845` 的守卫是「这一帧比上一帧晚 >1 秒」就认为发生了跳变。

## 改动

`app/src/main/cpp/slam_engine.cpp`：

- `Engine` 加 `rebaseSession`；`start()` 置位。
- worker 每趟处理第一帧时算一个 `sessionOffset`，让这一帧的 `t` 正好等于
  **上一趟最后一帧 + 33 ms**（`kSessionGapS`），后面所有帧沿用。
- **相机和 IMU 加同一个偏移**，相对时序一点没变 —— 变的只是这条时间轴的起点。

## 决策

**① 在 `slam_engine` 层解决，不动 ORB-SLAM3 的守卫。**
守卫本身是对的：真的跳了 20 秒，IMU 预积分确实不能当连续用。我们要消除的是
"这个跳变其实不代表任何东西"—— 两次会话之间没有数据，间隔多少都是任意的。

**② 不是把每趟的基准清零。**
清零会让新一趟的时间戳从 0 开始，而上一帧还在 t≈36 s ⟹ 走的是守卫的另一条分支
（`mLastFrame > mCurrentFrame`）：打 `ERROR: Frame with a timestamp older than
previous frame`，然后同样重建地图。两头都躲不开，只能**接续**。

**③ 间隔取 33 ms（一帧）。**
守卫的阈值是 1 秒，33 ms 安全；取太小也没意义，取大了会让"最后一帧到第一帧"
显得像有运动。

**④ 否决：改 `Tracking.cc` 里的 1 秒阈值。**
那是全上游共用的常量，调大只会把真跳变的检测也一起废掉。

**⑤ 否决：每趟重建 System。**
词袋要重载 38 秒，而且 atlas 还得重新读盘。

## 验证

**未重编、未真机**（需要重编后跑两趟）。

| # | 做什么 | 期望 |
|---|---|---|
| ① | 第一趟启动 | 日志**没有** `时间轴接续`（没有上一趟，偏移为 0） |
| ② | 结束 → 再点「启动」 | 出现 `[M5] 时间轴接续：偏移 -19.9xx s（上一趟最后一帧 t=36.xxx）` |
| ③ | 第二趟开头 | **不再有** `Timestamp jump detected`，也**不再有** `[M5] 地图被重置（第 1 次）` |
| ④ | 第二趟看地图统计 | 图数不因为这一趟凭空 +1；能直接在当前图里重定位的话，轨迹接着上一趟 |
| ⑤ | 回归 | IMU 初始化仍然要开头持续平移；存图/恢复/合并不受影响 |

如果重定位失败仍然新建了图，那是 ORB-SLAM3 的 LOST 路径，不是这条改动引入的 ——
§验证 ④ 要看的是"跳变守卫有没有触发"，不是"一定不新建图"。

## 遗留

- **会话之间的真实运动被抹掉了**：手机可能在 20 秒里换了个房间。IMU 的速度/偏置
  仍是上一趟的，第一段只能靠视觉重定位。这正是"Lost 之后重定位"的正常路径。
- **轨迹文件的时间戳变了**：`traj-*.txt` 第一列以前是"进程内第几秒"，现在接续上一趟。
  读轨迹的代码只用位置（`nativeReadTrajFile` / `transformTrajFile` 都不看时间），
  但拿它和外部数据对齐时要注意。
- **只在这一层解决**：如果以后有别的路径直接调 `TrackMonocular`（比如标定页），
  记得也要走 worker 的时间轴。
