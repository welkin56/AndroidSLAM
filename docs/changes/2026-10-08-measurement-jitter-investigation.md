## 决策

### 一、先造了三件诊断仪器（都没有留痕）

真机日志里**没有**相机位姿，也没有「这次是按什么规则选的点」，所以头两轮纯属瞎猜。
后面加了三个字段才看见真相：

| 字段 | 干什么 | 后来证明 |
|---|---|---|
| `候选N` | 吸附半径内有几个可用地图点 | **「点少」那半成立**：`候选1` 占 **40%** |
| `跨度X%` | 那些点深度的最大相对跨度 | **会骗人**，见下 |
| `移动Xcm` | 距上次打日志相机平移了多少 | 关键：把「手机动了」和「没动」分开 |

外加一条**心跳行**（读数没变也每 2 秒打一行）——
**没有它的话，「静止时很稳」和「这一段什么都没发生」在读日志时长得一模一样**，
而这两端正是判据。

### 二、⭐ 决定性判据：**共线检验**（不需要任何外部工具）

诊断日志只有「距离」和「目标的世界坐标」，没有相机位置。
于是造了一个**不依赖外参**的判据：

> 相机若真的没动也没转，它看着同一方向的两个目标**必须共线**，
> 于是 `|世界点A − 世界点B| ≈ |距离A − 距离B|`。

在「相机平移 = 0cm」的 85 秒静止窗口里跑：

```
    时刻     d1     d2   |Δd|  |Δ世界点|   比值
  68.6s   2.64   4.73   2.08     2.11    1.01   ✓
  70.6s   4.73   1.95   2.78     2.82    1.01   ✓
  共线占 42/50 = 84%        比值中位 1.02
```

**比值 1.02 ⟹ 那两个点在同一条视线上，一个 1.95 m、一个 4.73 m。**

**结论：手机没动也没转，十字指着同一个方向，读数在 1.95 m 和 4.73 m 之间来回换。**
那 85 秒里 **59% 的相邻读数换了目标**，**23% 的读数变化超过 10%**，最大 2.82 m。

**根因**：每帧独立地「取半径内最近的地图点」，而**这一帧哪个点被匹配上是逐帧波动的** ——
`Tracking.cc:2229` / `:2266` 会把 `mvpMapPoints[i]` 置 `NULL`（没匹配上 / 被当外点剔掉）。

> ⭐ **这条判据本身值得带走**：只要有「目标的 3D 位置 + 到它的距离」，
> 就能在不引入任何外参、任何新日志字段的前提下，判断相机是否真的静止。
> **这次就是靠它把「用户在动」这个混淆项彻底排除掉的。**

### 三、⭐ 有效的修法：**目标身份锁定**（但本轮没保留）

**用户在第 2 轮亲口确认过它有效：「跳的比较小」。** 那正是引入锁定之后。

做法（**只在 `measure_center` 内部，JNI / Kotlin / 布局一个字不用动**）：

1. **跨帧记住盯住的那个 `MapPoint*`**（`CenterMeasureState`）。
2. **成立条件不看它这一帧有没有被匹配** —— 世界坐标是不变的：
   ```
   pc = Tcw · P_world;   θ = atan2(‖pc.x, pc.y‖, pc.z)
   成立 ⟺ !isBad() && pc.z() > 0 && θ ≤ kLockAngleRad
   ```
   `θ` **不需要内参**就能算 —— 这正是「未匹配的帧也能维持锁定」的关键。
3. **`kLockAngleRad` 必须比吸附半径宽**（滞回）：吸附半径是 `kSnapFrac·w` 像素，
   而 `θ_max = 半径 / fx`；第一版把两者取成一样宽，结果是
   **在半径边缘选中的点下一帧就锁不住**，只好重选 —— 读数就在边缘来回跳。

**顺带的好处**：34% 的「目标丢失」里大部分是「锁定的点这一帧没被匹配」，锁定之后不再掉。

### 四、⚠️ 被真机数据推翻的两个设计（我自己提的）

**① 「遮挡先验」：按深度取「最近的那一层」—— 错的。**

当时的论证是「十字那条视线上，近处物体会挡住远处，所以最近那层才是你看到的」。
**那个论证预设了近点是真实物体。** 真机数据显示：

```
0.787 m  像素(323.5, 228.9)  候选7  跨度447%
0.545 m  像素(323.5, 228.9)  候选9  跨度627%
1.457 m  像素(323.5, 248.8)  候选6  跨度172%
```

**这些读数全落在 11.6 px 处**（吸附半径 12.8 px 的**边缘**），
而稳定的读数都在**离中心 2~5 px** 的地方。

**几何上它们是坏点**：同一个帧里近点和远点**同时被匹配**在十字附近，
但一个 0.55 m 处、离光轴只有 1.5 cm 的实体**会把整个画面填满**，
它后面的 4 m 表面不可能在同一个像素上还被看见。**两个深度不可能都对。**
而远点那一组有 8~11 个点、跨度只有 1~20%（自洽的表面），近点只有零星一两个还闪烁。

> **稀疏 SLAM 里三角化错的点，恰恰长成「几乎在光轴上、深度却很小」的样子。**
> 所以「取最近层」这条规则**系统性地专门挑中坏点**。

**② 「让位」规则：锁定期内出现明显更近的点就切过去 —— 错的。**
同源。它只触发了一次，而那次让位给的正是一个坏点。

### 五、⚠️ 第三个被推翻的：**获取去抖**

为了治「挪开再回来数值变化大」，加了一道：取新目标前，先看最近 4 帧「最近那个候选」的
深度稳不稳（跨度 ≤25%），稳才采纳。

**效果：丢失率 20% → 39%。** 因为它每次锁掉都要重新攒 4 帧。
**没有任何可见收益** —— 见「验证」最后一节。

### 六、⚠️ 「把中值窗口调大」是**错的工具**

我一度认为窗口是参数问题。**不是。**

| 窗口要压的 | 量级 | 中值窗口能压吗 |
|---|---|---|
| 位姿估计噪声 | **毫米** | ✅ |
| 层间换人 | **米** | ❌ |

**「一半样本在 1.95 m、一半在 4.73 m」这种双峰输入，5 帧中值只能输出 A 或 B。**
中值对**离群点**鲁棒，对**双峰分布**无能为力。
**压随机噪声**和**防止换错目标**是两件事，不能互相替代。

### 七、为什么全撤

用户决定：**只保留独立、明确的那一处（崩溃修复）**，测距那摊整体撤掉。
理由是这个项目一贯的判据 —— **能不能用一句话说清它干了什么**。
本轮测距的改动是「一个有效修法 + 两个被推翻的设计 + 一个回归」缠在一起，
**说不清**，而且**只有一次观察撑着**（用户那句「跳的比较小」），
没有干净的 A/B。撤掉、把结论沉淀下来，比带着一包不明所以的改动往前走更值。

## 验证

**以下都是真机跑出来的数。**

**1. 「跳变」是真的，且不是用户在动** —— 见「决策」二的共线检验（84%、比值中位 1.02）。

**2. 锁定之后还剩多少噪声 —— 毫米级**

同一个目标 + 相机平移 = 0，相邻两次发布的距离差：

```
26 对    中位 4.0 mm    90 分位 13.0 mm    最大 14.0 mm
```

**3. 各版本的丢失率（同一套三段跑法）**

| 版本 | 丢失率 | 备注 |
|---|---|---|
| 第一版修复（纯锁定 + 遮挡先验 + 让位） | **8%** | 用户「跳的比较小」 |
| 第二版（删遮挡先验、删让位） | **20%** | |
| 第三版（+ 获取去抖） | **39%** | **去抖是纯回归** |

**4. ⚠️ 一次差点误判的教训**

第三版那趟，全趟只有 **43%** 的读数落在用户说的真值（≈4 m）附近，
我一度以为「问题很大」。**但把时间轴打出来一看**：

```
20:51:43 ~ 20:52:15   读数 1.433 / 1.559 / 1.675 / 1.777 / 1.975 ...
20:52:43 ~ 20:53:14   读数 1.671 / 1.892 / 1.969 / 1.991 / 2.100 ...
```

**这两段是用户对着别的东西**（问过，确认了）。
而最后 12 秒（他确认对着 4 m 目标的那段）：

```
20:53:19  2.100  ✗
20:53:20  3.017
20:53:22  3.633  ✓
20:53:23  3.711  ✓
20:53:26  目标丢失
20:53:29  3.584  ✓
```

**基本是对的。**

> ⭐ **教训：用「全趟正确率」当指标之前，先确认「整趟瞄的是不是同一个东西」。**
> 否则会把「用户换了目标」算成「算法出错」—— 差一点就据此往下改。

**5. 未验证**

- **锁定没做过干净的 A/B。** 只有用户一次定性观察（「跳的比较小」），
  而且那一版同时还带着后来被证伪的遮挡先验和让位。
- **那些「坏点」是不是真的坏，没有独立证据**（只有几何矛盾这个论证）。
  没查过它们的三角化角、被观测次数、`mnFound`。
- 去抖在「防止锁到坏点」上到底有没有起作用 —— **没有对照，不知道**。

## 遗留

### 下次接着做，从这里开始

**已经验证站得住的（可以直接用）**

1. `CenterMeasureState { MapPoint* locked; float px, py; }` 跨帧记忆。
2. 锁定成立 = `!isBad() && pc.z()>0 && θ ≤ kLockAngleRad`，**不要求这一帧被匹配**。
3. **`kLockAngleRad` 取吸附角度的 2 倍**（滞回必须「释放比获取宽」）。
4. 选点**取半径内离十字最近**的（**不要**按深度分层）。
5. 中值窗口 **3 帧**、**连续缺 3 帧才清**。
6. 日志留 `候选N / 跨度X% / 新选|沿用` —— **它们是验收的依据**。

**还没解决的**

- **「坏地图点」没有识别手段。** 上面只证明了「取最近层会挑中它们」，
  没做到「把它们剔掉」。可疑的信号：**被观测次数少、三角化基线短、孤立**。
  `MapPoint` 上有 `mnFound` / `mnVisible` / `GetObservations()` —— **一条都还没查**。
- **「目标丢失」的来源没有拆开**：是「这一帧没匹配」还是「被剔成外点」。
  两者对应不同的处理。
- **`跨度` 这个字段会骗人**：它只统计**这一帧被匹配上**的点，
  所以「两次都是 `候选1 跨度0%`」也能是相距 2.8 m 的两个点。
  **别只看它下结论**（这一条我踩过）。

### 一条方法论

**这轮我三次凭部分数据下结论、三次被真机推翻**（遮挡先验、让位、把窗口当参数问题）。
每一次的错法都一样：**从几行日志里归纳出规则，而没有先把「日志里没有的东西」找出来**
（相机位姿、点有没有被匹配、用户瞄的是不是同一个东西）。
