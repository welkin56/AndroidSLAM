# 2026-10-17 重定位（②a）—— 让载进来的图**认得上**

> ## 📦 归档说明（2026-10-17 收尾）
>
> **这批代码没有合入主干，保存在分支 `feat/relocalization`。**
>
> 原因：按用户定的判据 —— 「如果②b（认出来之后手动合并）的精度和回环一样，就继续做；
> 不一样就存档不做」。真机实测**不一样**：
>
> | | 平移 \|t\| | 转角 |
> |---|---|---|
> | 重定位的单帧变换 | 1.121 m | 15.2° |
> | 回环的多帧 Sim3 | 1.495 m | 26.3° |
>
> 两者互为逆（模长、转角在取逆下不变），所以是**直接可比**的：差 33% 平移、11° 转角。
>
> 根因：单帧变换是**构造出来让相机脚下那个点正好对齐**的；两张图相对彼此有非刚性的漂移，
> **不存在处处正确的刚性变换**。合并要动整张图，要的是全局拟合 —— 回环的多帧 Sim3 更好，
> 而且不是好一点。想追平就得自己写多关键帧 + Sim3，那就是把回环重写一遍。
>
> ⭐ **真正值钱的是下面四轮真机跑出来的结论**（尤其是「走 10 秒」和「回环在 BA2 前沉默」），
> 比代码重要。将来谁再想做这条路，先看「追加」那几节。

一句话：按下「重定位」，在 atlas 的**所有图**里找当前画面。连续几次都落到同一片区域
才算认出来，然后把旧图按算出的变换**叠到 2D 小窗上**。

**这次不改图。** 只回答「认不认得出来、认到哪张、那两张图在空间上怎么对」。

## 动机

① 交付的是「图确实进来了」，但载进来的图**够不着、也用不上**：
`Tracking::Relocalization()` 查候选时传的是 `mpAtlas->GetCurrentMap()`（`Tracking.cc:3638`），
而载入后当前图是构造函数新建的**空图** ⟹ `DetectRelocalizationCandidates` 收尾那行
`if (pKFi->GetMap() != pMap) continue;` 把旧图的关键帧全跳过 ⟹ 候选恒为空。

用户把 ② 拆成两步：**②a 重定位能用起来（这次）→ ②b 真合并**。

②a 不只是「前置」：两图之间那个变换的推导、应用和**验证**都在这里
（叠画对得上 = 变换对）。②b 只剩「合并」那一坨。

## 决策

### 一、⭐ 搜**所有图**，不预先挑一张

原计划是「挑关键帧最多的那张，只在它里面找」。否掉，两个理由：

1. **「我在哪张图里」正是重定位的本职** —— 让算法用实际画面回答，而不是我们按数量猜。
2. **预先挑会踩一个坑**：`DetectRelocalizationCandidates` 的阈值是**在「所有图」上
   归一化**出来的（`bestAccScore`、`maxCommonWords`），而图过滤在**最后一步**。别的图的
   KF 能把阈值抬高，把目标图里本来够格的候选挤到线下 ⟹ **假报「没候选」**。
   不预先挑就没有这个问题 —— 全局比分数正是想要的行为。

落地就是 `pRefMap == nullptr` 表示不过滤，收尾那行加个 `pMap &&`。

**顺带**：APP_DESIGN §10 那个「多张旧图怎么选」的洞**自动消失**，`PickLoadedMap()` 不做。

### 二、⚠️ 探针必须**只读**，而且不是靠复制函数

`Relocalization()` 成功时会写 `mnLastRelocFrameId = F.mnId`。那**不是书签，是行为开关**：

| 行 | 作用 |
|---|---|
| `Tracking.cc:1962` | 接下来 2 帧不用运动模型，强制 `TrackReferenceKeyFrame()` |
| `Tracking.cc:3111` | 30 帧内不许插新关键帧（**条件是 `nKFs > 30`**，主场景不触发） |
| `Tracking.cc:1978` | 跟丢时**更早**判 LOST（跳过 IMU 硬撑的 5 秒） |
| `Tracking.cc:2184` | 那个窗口里每帧 `new Frame` 且**从不释放**（上游死代码泄漏） |

作者的意图是对的：重定位意味着位姿**不连续地跳了一下**，tracker 该保守一秒。
但 ②a 的探针**没有发生那种跳跃**。

**修法：一个内核 + 两个薄壳**，不是复制一份 165 行的函数。

```cpp
bool RelocalizeInternal(Frame& F, Map* pRefMap, KeyFrame** ppMatchedKF, int* pReason, bool bCommit);
bool Relocalization() { return RelocalizeInternal(mCurrentFrame, mpAtlas->GetCurrentMap(), nullptr, nullptr, true); }
```

内核里唯一的 `bCommit` 守卫就是那一行。`bCommit=true` 时 `F` 就是 `mCurrentFrame` 的别名，
**上游行为一字不变**。

⚠️ **量级要说准**：探针是有限时长的（采集窗口约 0.6 秒），确认/失败后立刻停 ⟹ 那个
「保守窗口」最多续到「采集窗口 + 1 秒」，**不是永远**。真正值得防的是
「探针到下一帧之间没人读 `mCurrentFrame`」这个**隐式约定** —— 一次 Frame 拷贝
~200 KB、10 次/秒，不值得为省它留个坑。

### 三、⭐ 连续一致才算认出来

ORB-SLAM3 自己合并前要求 `mnMergeNumCoincidences >= 3`。我们照这个精神做，判据三条：

- 连续 **6 次**探针都成功（每 3 帧一探 ⟹ 约 0.6 秒）
- 命中的 KF 与**第一次**命中的 KF **共视**
- **相邻两次解出的位姿差不超阈值**（0.2 m / 5°）

三条任何一条断了就重数；探满 16 次还凑不齐 ⟹ 报「前后不一致」。

**为什么用「位姿差」而不是「多等几个 KF」**：站着不动时位姿几乎不变 → 很快确认；
每次都定到**不同的**柱子（典型感知混淆）→ 位姿跳变 → 判为不一致。
（每次都定到**同一个**错误地方的情况挡不住 —— 那是 §4.5 人眼的活。）

**为什么 ②a 就要这个**：②b 的合并认错的代价是「整个当前图被变换着灌进目标图的错误
位置」—— **教的那张图被污染**。这个判据是唯一挡得住它的东西，必须在 ②a 就立起来。

### 四、⭐ 叠画用的是**反方向**的变换

两图变换有两个方向，混了就全错：

| 方向 | 公式 | 谁用 |
|---|---|---|
| 当前图 → 目标图 | `T_X<-N = T_wc_X · T_cw_N` | ②b 合并（就是 `mSold_new`） |
| **目标图 → 当前图** | `T_N<-X = T_wc_N · T_cw_X` | **②a 叠画** |

写反之后旧图会落在错位的地方，**看起来像「重定位定错了」** —— 这是最容易误判的一种错：
你会去调判据，而真正错的是方向。

**两层都是刚性变换（`s = 1`）**：两张图都 IMU 初始过，尺度都是米 ⟹ 不需要估 Sim3。
§3 当年估的「Sim3 是最糙的部分」根本不适用。

### 五、跟踪没 OK 就不给叠图

`T_cw_N` 取的是探针**之前**当前帧的位姿。跟丢时那一帧**没有有效位姿**，拿它算出来的
变换是错的 ⟹ 旧图会叠歪 ⟹ 用户会以为「变换算错了」，从而**错误地否掉 ②b**。

所以：`mState == OK` 才给变换，否则只报「认出来了」不给叠图（`GetRelocMapAndTransform`
返回空，`GetRelocMapPoints` 返回 0，小窗上没有那一层）。

### 六、按钮看 `slamRunning`，不看有没有旧图

§2.4 写的是「只看 referenceMap 是否为空」。改掉：**在跑就能按**。

没载图时它认的是自己刚建的那张图 —— §2.4 第二种场景（停止 → 再启动接回来）用的就是它，
而且那是**现在唯一**能救回停止后位姿的路：单目惯性 + 非定位模式下，
`Relocalization()` 根本不会被自动调到（三处调用两处在 `mbOnlyTracking` 里、
一处在非惯性分支）。

### 七、⭐ 回环检测本来就会自动跨图合并 —— 这条写进文档，但不干预

`DetectNBestCandidates` 从倒排表（所有图）收候选，按 `GetMap()` 分两类
（`KeyFrameDatabase.cc:712-728`）：同图 → 回环候选；**不同图 → 合并候选**。命中就
`MergeLocal2()`，把另一张图的 KF/MP **全部搬进当前图**。

⟹ **载入旧图后不按按钮、一直走，它自己也可能合上**（门槛：当前图 ≥ 12 KF 且 IMU BA2 完成）。
这不是我们做的，也不需要拦。**但验证时要知道**，别把自动合并当成我们的功劳。

## 追加（2026-10-17）：入口页改选地图不生效，而且看不出来

**现象**（用户上报）：载入一张旧图 → 退到入口页 → 改选「新建地图」→ 状态栏文字
和刚才**一模一样**。

**根因**：两个「地图」不是一回事，界面只显示了其中一个。

| | 谁拥有 | 什么时候定 |
|---|---|---|
| 入口页这次选的（`mapFile`） | 每个 `MainActivity` 实例 | 进这一页时 |
| `System` **实际吃**的 | 进程级（`slam::init` 只生效一次） | **构造那一刻** |

`slamState == SLAM_READY` 之后状态栏那行**根本没有地图名** ⟹ 选哪张文字都一样。
而且**再选不会生效** —— `System` 不销毁（§5 决策一），换地图只能重启 App。

**改法**：不是「让选择生效」（那要重建 `System`，等于重付 38 秒，旧的那个也没法安全
销毁），而是**把真相说出来**：

1. `slam_engine` 记下构造时那条路径（以前只记了 `loadWanted` 这个 bool）⟹
   `loadedMapPath()` → JNI `nativeLoadedMap() → String`。
2. 状态栏两处带上**实际**那张：「已就绪（吃的是 X）」「词袋加载中…（吃的是 X）」。
3. 两者不一致时，正文最上面两行：入口页选的是 X、但吃的是 Y、换地图要重启 App。

**验证**：`assembleDebug` + `installDebug` ✓。真机行为待确认。

真机日志（`adb logcat -s slam`）把问题一次说清了：

12:27:10.625  Timestamp jump detected → Creation of new map with id: 2
12:27:29.881  *Merge detected → Merge finished!      ← 回环自动合并 #2

### 📌 一、⚠️ **自动合并真的在工作** —— 而且很快

初始化后 **16 秒**就合上了，一次会话合了两次。⟹ **②b（手动触发合并）的必要性要重新评估**
—— 自动的虽然慢，但它会动。（用户问「既然回环能合还要重定位干什么」，
答：合并回答「这两张图是不是同一个地方」，重定位回答「我现在在哪」；
而且合并有 `< 12 KF` 的门槛、没有「只看不合」的模式、失败是静默的。）

### 📌 二、⚠️ **`停止 → 再启动` 会直接开一张新图**

`12:27:10` 那行 `Timestamp jump detected`：两帧之间隔了 7 秒（用户按了结束再启动），
而 `e.base` 是整个进程只取一次的首帧基准 ⟹ 时间戳直接跳 ⟹ `CreateMapInAtlas()`。

**⟹ 每停一次就多一张图**，atlas 才滚那么快。这不是 ②a 引入的，是既有行为；
但它把「停止后再启动接回去」（§2.4 第二种场景）变成了「又开一张图，等回环来合」。

### 📌 三、⚠️ **重定位失败的真正原因：判据写得太严**

探针 #1→#3 连续对上了（`dpos` 3.6 cm / 1.7 cm，共视都成立），**第 4 帧 `reason=1`
就一帧单杀**，把 3/6 的采集掐死。

**改法**：加「连续没结果」计数 —— 连续 **3** 次探不出东西才下结论，
`kRelocMaxProbes` 从 16 提到 20（现在数的是**尝试次数**，不是成功次数）。
和 ORB-SLAM3 自己的 `mnMergeNumNotFound` 一个意思。

### 📌 四、命中「当前图」时不该有绿色 —— 这次没有是**对的**

两次合并之后 atlas 里只剩一张图（另一张被搬空），所以重定位只能命中当前图自己。
原实现会把当前图**单位变换后再叠一遍**（计划里写了「命中当前图不叠」，代码漏了），
现在补上：`mpRelocOutMap` 只在命中**别的图**时才设。状态栏也分开说
「就是当前图」/「认出了另一张图」。

### 📌 五、为什么「把重定位接到回环检测上」只对一半

用户提的方向。**合并那半截早就接上了**（②b 计划里就是复用 `MergeLocal2`，
不改它的搬移逻辑）。**检测那半截接不过去**，三条：

1. `NewDetectCommonRegions()` 开头 `if(mpLastMap->GetAllKeyFrames().size() < 12) return false;`
   —— 而按按钮最需要的时机正是「刚载入、新图才几个 KF」。
2. 它没有「只看不合」的模式，检测成功直接进 `MergeLocal2` 改图；而 ②a 的全部价值
   就是先看一眼。
3. 它按关键帧跑，按钮没有关键帧可喂。

### 📌 六、⚠️⚠️ **重定位的结果在地图重置之后必须作废**（第二台真机跑出来的）

日志：`12:40:32` 六个探针全部命中 **图 0（当前 1）**、结论 `认出来了：另一张图（第 1 张，
id 0），183 个关键帧` ✓。然后 `12:40:55 → 12:41:03` **地图被重置了 4 次**，
`12:41:19` 回环自己合并了一次 —— 用户看到绿层**偏了**，而回环合并的位置是对的。

**根因**：`ResetActiveMap()` 清空当前图之后，`MonocularInitialization()` 用新的第一对
关键帧**重新锚定原点**。`Map::mnId` 不变（还是「当前图」），但**坐标系换了**。
而绿层用的是「图 0 的点 × 一个基于**旧**当前图坐标系算出来的 `T_N<-X`」⟹ 整体偏移。
回环用的是**重置之后现场算的 `ComputeSim3()`**，所以它不错。

**⟹ 任何「跨图变换」都和当前图的坐标系绑死，重置就等于把它作废。**

改法：新增状态 **6 = 结果已失效**，`Tracking::Reset()` / `ResetActiveMap()` 开头调
`InvalidateRelocalization(6)` —— 清 `mpRelocOutMap`（不再把图交出去）、置状态 6；
引擎在检测到 `kfCount == 0` 时同时清掉点云快照；界面说
「结果已失效（地图被重置，坐标系换了）—— 要用请再按一次」。

⚠️ **合并（`MergeLocal2`）也会换当前图的坐标系**（`ApplyScaledRotation`）。
我一度以为它「会自愈」（被合并的图被搬空 ⟹ 枚举到 0 个点）—— **错了**：
小窗那层是**快照**，建一次就靠 `relocSnapAtMs != 0` 挡住重建 ⟹ **根本不会再问一次**，
绿层就一直画着那份合并前的点。而且状态码还停在 4（重置才作废，合并没人通知）。

**补上**：`ProcessRelocRequest()` 每帧顺手看一眼 —— 状态还是 4、但
`mpRelocOutMap->KeyFramesInMap() == 0`（被搬空）⟹ 调 `InvalidateRelocalization(6)`。
状态文案也跟着改成「地图变了：重置或合并」。

### 📌 七、⚠️⚠️ **「搜所有图」会把当前图也搜进去 —— 而它总是赢**（第三轮真机）

日志里每一次结论都是：

```
[RELOC] 认出来了：就是当前图（第 4 张，id 3），28 个关键帧；同一个坐标系，不用叠
[RELOC] 认出来了：就是当前图（第 4 张，id 3），273 个关键帧；同一个坐标系，不用叠
```

**新图和旧图拍的是同一个地方**，词袋分数一样高；而当前图是**刚拍的**，往往还更匹配几条。
⟹ 重定位永远命中自己，绿层一次都没出过，探针在两张图之间来回跳
（`图 2（当前 3）` / `图 3（当前 3）` 交替，连续计数反复归零）。

**这是决策一（搜所有图）的代价**：算法分不出「同一个地方被录了两遍」。
而 ②a 要的从来不是「我在哪张图」，是**「我能不能接回磁盘上那张图」**。

**改法**（决策一的修正，不是推翻）：`DetectRelocalizationCandidates` 加 `pExcludeMap`，
候选里一律不收那张图。`ProcessRelocRequest` 里的规则：

| 情况 | 搜谁 |
|---|---|
| atlas 里还有**别的非空图** | **排除当前图**，只搜那些 |
| 只剩当前图一张 | 不排除（这时「认自己」才有意义）|

⟹ 载入旧图 → 只认旧图 ✓；停一次再启动（会开新图、旧图还在）→ 只认旧图 ✓；
回环合完只剩一张 → 退回「认自己」✓。

### 📌 八、⚠️⚠️ **②a 真正的前提是「会话要稳」，而它要求的动作和直觉相反**（第四轮真机）

第四轮：**走起来之后通了** —— 重定位认出旧图（`图 0（当前 1）`、183 个关键帧），
之后回环自己把它合上。

但前面几轮全卡在同一个地方：`Not enough motion for initializing. Reseting...`。
判据在 `LocalMapping.cc:131-145`：

```cpp
float dist = |C(上上个KF) − C(上一个KF)| + |C(上一个KF) − C(当前KF)|;
if(dist > 0.05)  mTinit += 两个 KF 之间的时间;
if(!GetIniertialBA2() && mTinit < 10.f && dist < 0.02)
    → 重置当前图
```

**IMU 第二次 BA 完成之前，必须连续走够 10 秒（每个关键帧之间至少挪 5 cm）。
站着不动 ⟹ 位移之和 < 2 cm ⟹ 必然重置，一直到 BA2 完成。**

⚠️ **所以我之前写在界面上的「站定别动」是错的** —— 它和 IMU 初始化的要求直接打架，
会让人站在那儿把会话反复重置掉，重定位的结果根本活不到确认。已改成
「照常走，别停」。

顺带把探针的位姿门槛放宽：`0.20 m → 0.35 m`、`5° → 8.6°`。
探针间隔约 0.1 秒，走路 1.4 m/s ≈ 0.14 m，原来的门槛是给「站着」留的余量太小。
这个门槛的作用不是防抖，是挡住「两次定到相隔很远的两处」。

### ⭐ ②b 的结论：**先不做**

自动合并在会话稳住之后**确实会把两张图合起来**（这一段一共触发了 3 次）。
⟹ `载入旧图 → 走 → 接上` 这条链**不用 ②b 也能走通**。
②b（手动触发 `MergeLocal2`）的价值只剩「不用等回环、第一秒就合」。
等真的频繁撞上「回环半天不合」再回来做。

## 遗留

- ⚠️ **②a 里认出来之后没有任何后果**（不切图、不合并）。小窗上那一层是唯一的可视化。
  这是刻意的 —— 先把「能不能认出来」验证掉。
- ⚠️ **自动合并一直在后台跑**（决策七）。验证时别误判成我们的功劳。
- ⚠️ **单帧算出的变换精度**：真机上叠出来的绿层有「一点偏差」（几厘米量级）。
  来源三个：`T_cw_N` 的跟踪误差、`T_cw_X` 的 PnP 误差（日志里探针间 `dpos` 3～8 cm、
  `drot` 0.5～2°，就是噪声地板），以及**最主要的** —— **两张图各自的漂移**：旧图是上一次
  会话建的，同一处空间在两套图里本来就差几厘米到几十厘米。

  ⚠️ **一个刚性变换不可能同时对齐整张图**（漂移在空间上变化，不是常数）。
  真正的对齐由合并后的 `MergeInertialBA` 联合优化完成 —— 绿层只是**预览**。

  想再准一点：把 6 次一致探针的 `(T_cw_N, T_cw_X)` 平均后再算变换。能压随机噪声，
  **压不掉**两图之间的系统性漂移差，收益有限，没做。
- ⚠️ **探针占 CPU**：采集窗口里每 3 帧跑一次完整重定位，会挤掉正常跟踪的帧。
  没实测挤掉多少。
- ⚠️ **`mnRelocQuery` 那个缓存按帧号去**（`KeyFrameDatabase.cc:751`）。探针用的是副本，
  帧号相同 ⟹ **同一帧不能探两次**。现在「每 3 帧一探」天然满足，改频率时注意。
- ⚠️⚠️ **① 的雷：`Atlas::PreSave()` 会把空的当前图标坏 ⟹ `GetCurrentMap()` 死循环。**
  它遍历整个 `mspMaps`，包括当前图；0 KF 的图被 `SetMapBad`，而 `mpCurrentMap` 仍指着它，
  之后任何 `GetCurrentMap()` 都卡在 `while(IsBad()) usleep(3000)`（还抱着 `mMutexAtlas`）
  ⟹ Tracking 和 LocalMapping 同时卡死。现在只靠 Kotlin 侧「KF=0 时不让存」拦着，
  `SaveAtlasTo()` 没兜底。**不在 ② 修**（顺手改会让空图进存档，得单独想）。
- **`§4.2` 第 2 层（限制候选到路径点附近）仍然不做**。
- **地图会一直涨**（用户提过想加关键点/关键帧的淘汰）。合并不是回答这个的，
  那是 `KeyFrameCulling` / `MapPointCulling` 的调参问题，单独一批。
- **`MainActivity.kt` 的注释还没收敛**（1400 行）。
- **`InitializeIMU` 的 NaN 崩溃**仍未处理。
- **存档仍然写整个 atlas**（① 的遗留）。
- ⚠️ **「换地图要重启 App」—— 根因和一条可行的解法。**

  `System` 无法销毁（上游 `Shutdown()` 不 join 线程，等待那段被注释掉了）、词袋每个
  `System` 各读一遍（本机 ~38 s）、`LoadAtlas` 不能调第二次（它恢复文件里的静态 ID
  计数器，和内存里已有的图撞号）。三条合起来 ⟹ 换载入的图 = 换进程。

  **但有一条不用重启的路**（用户 2026-10-17 提的，**这次不做**）：

  ```
  System::Reset()          // Tracking::Reset()：清倒排表、清 atlas、ID 归零；【词袋不动】
  LoadAtlasInto(path)      // 新增：ia >> *mpAtlas（读进现有对象，不是换指针）
  mpAtlas->CreateNewMap()  // 和构造函数最后那句一样
  ```

  现状卡在第二步：`LoadAtlas` 是 `ia >> mpAtlas` ⟹ **换掉指针**，而
  `mpTracker` / `mpLocalMapper` / `mpLoopCloser` 各自攥着旧 atlas 的指针。
  改成读进 `*mpAtlas` 就绕开了 —— 对象身份不变，线程不用改指向。
  代价从 38 s 降到几秒（只反序列化图）。

  **三处风险，做之前必须先验**：
  1. `Tracking::Reset()` 我们**从没跑过**（真机走的是 `ResetActiveMap()`）。它里面
     `clearAtlas()` 只清指针不删对象（KF/MP 泄露），而静态 ID 计数器被归零 ⟹
     新对象可能复用旧对象的 ID。旧对象已不可达，理论上无害，没验过。
  2. `RequestReset()` 是**阻塞**的（等 LocalMapping / LoopClosing 回应）⟹ 必须排在
     SLAM 线程上，不能从主线程调。
  3. boost 反序列化进**已有内容**的对象 —— 要确认 `serialize` 读 vector 前会先清空、
     `PostLoad` 末尾会 `mvpBackupMaps.clear()`。
