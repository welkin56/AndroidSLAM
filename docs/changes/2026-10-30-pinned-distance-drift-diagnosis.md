# 2026-10-30 两点距离会变、标记会偏：先加观测再改

一句话：折线的点存的是**地图点身份**、每帧问它要最新世界坐标，所以距离只可能因为
「两个点在世界里相对动了」而变。能让它们相对动的机制有三种，现象一模一样 ——
这次**只加日志**，把三种分开，不动测距逻辑。

## 动机

用户报的现象（真机）：

> 「测量了两个点之间的距离之后，到处走、转动视野之后，发现两点之间距离变了，
> 标记也和我标的位置偏移了一点。对着它左右晃动，也会让距离有一点变化。」

现有链路（`slam_engine.cpp::getPinned`）：

```
按「加点」时：存 MapPoint* 身份 + 那一刻的世界坐标
之后每帧：pw = mp->GetWorldPos()（BA 一直在挪它）→ 距离 = |pw_A − pw_B|
```

数字变 = 那两个点在世界坐标里相对彼此动了。可能的来源：

| 来源 | 代码位置 | 是什么 |
|---|---|---|
| A 整图改尺度 | `LocalMapping.cc` → `InitializeIMU` / `ScaleRefinement` → `Map::ApplyScaledRotation` | 第 5、15 秒，以及 mTinit 25/35/45/55/65/75 秒各一次；**所有米制量同比例变**。点云和关键帧位姿一起缩放，所以画面上的投影不变（标记看着不跑），但距离变 |
| B 局部 BA 挪点 | `Optimizer::LocalBundleAdjustment` | 每个关键帧都在微调，两点收敛速度不同 ⟹ 距离和标记都慢慢变 |
| C 点被剔除后冻结 | `getPinned`：`if (mp && !mp->isBad()) pw = ...` | 走开、点出了视野就可能被 `MapPointCulling` 剔掉，该点坐标**永久停在剔除那一刻**，另一个点继续收敛 |

另有 D：钉点本来就不是十字指的那个点 —— `measure_center.cpp` 的锚点是
`kSnapRadiusPx = 20` 内最近的地图点，3 m 处 20 px ≈ 14 cm。

## 改动

只加日志，**没有一行改变行为**。

**`slam_engine.cpp`**

- `Engine::Pinned` 加 `pw0[3]`（钉下时的坐标，只用于算漂移）和 `sawBad`（剔除事件只打一次）。
- `Engine` 加 `lastW / lastH`（把像素偏差换成米要用图宽）和 `pinnedLogAtMs`。
- 抽出 `refreshPinned()`，`getPinned` 和日志共用同一套刷新规则。
- `addPinned()` 打**钉点日志**（每个点一行）：
  ```
  [M6] 钉点 #1 地图点 12345 质量2 路径1 跨度21% 像素偏差14.3 px(≈0.115 m) 距离3.214 m
  ```
  `像素偏差` = 锚点像素到画面中心的距离 —— **D 有多大，这里直接读**。
- `logPinnedDrift()`：每秒一行（只列前 6 个点）：
  ```
  [M6] 钉点2  段1 1.234/1.241  点1 id12345 bad0 Δ0.012  点2 id12346 bad0 Δ0.034  camR 1.234 KF 87
  ```
  - `段1 当前/钉下时`：数字变了多少，直接对比；
  - `点N Δ`：相对钉下位置的位移，看两点是不是各走各的；
  - `bad`：该点是否已被剔除（日志里还会有单独一行 `被剔除，坐标从此冻结`）；
  - `camR`：相机世界坐标的模长，**整图缩放的指纹**。
- 挂在 worker 上，**关掉测距开关也继续打**，否则看不到后半程。

## 决策

**① 先观测，不改逻辑（用户要求）。**
三种机制看起来完全一样，但修法相反：A 改不了（那是"米"在被修正，冻住它反而是冻住错误）；
B 只能靠更好的锚点（多点中值）；C 要换成「重新认点」。**不先分开就动手，多半修错地方。**

**② 记 `camR` 而不是只记段长。**
`ApplyScaledRotation` 是以地图原点为中心缩放整张图，所以相机到原点的距离和段长会
**按同一个比例**同时跳。只有段长变、camR 不变 ⟹ 是 B 或 C。这一条是区分 A 的关键。

**③ 钉点时记「像素偏差」。**
如果标记一开始就偏了十几厘米，那是 D，和后续漂移无关；先把它量出来，别混算。

**④ 每秒一行，不是每帧。**
15 Hz × 几十个点 × 几分钟会把 logcat 淹掉，而漂移是秒级的现象。

**⑤ 否决：读数改成"十字光轴上的点"（我改过，已撤回）。**
想法是「深度仍取锚点的，横向按十字算」，这样钉下去正好是十字指的位置。
**错在十字处常常没有地图点**，等于借了旁边那个点的深度 —— 只有当锚点附近是
同一块连续表面时才成立。而人爱量的恰恰是墙角、桌沿这种深度跳变的地方，
那里借来的深度是错的，**而且画面上看不出来、也不会报「不太准」**。
用一个看不见的假设换一个看得见的偏移，不划算。

**⑥ 否决：直接「重新认点」（C 的修法）这次先不做。**
它是对的，但会改坐标（认到别的点上），在还不知道 C 占多少之前做，
会把观测量和修法混在一起，出了问题分不清是谁的。

## 遗留

- **三种机制的修法都还没做**：A 最多做提示（"地图还在收敛"）；B 考虑锚点取邻近多点中值；
  C 做成「按世界坐标重新认点」。
- **只在当前帧匹配到的点里找**是不行的（C 的修法需要**整图**点），
  那时要么用 `System::GetAllMapPoints()`（要评估 15 Hz 下拷贝几千个点的代价），要么限制到 1 Hz。
- **`mp == nullptr` 的钉点**（平面兜底来的）没有身份，永远冻着，这次也在日志里（`id0`）。
- **段长仍在每帧重算**，标签用 0.5 mm 的阈值防抖 —— 那是显示层的事，不影响这次的判读。
