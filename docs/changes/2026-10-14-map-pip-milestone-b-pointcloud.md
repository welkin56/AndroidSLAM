# 2026-10-14 2D 地图里程碑 B：点云 + **固定比例** + 加减缩放 + 小地图开关

一句话：小窗里加**地图点云**，但先把 A 的**自动 fit 拆了** —— 比例改成**固定的、用户按加减调**，
中心跟着当前位置走。点云只画**当前高度附近那一层**，看到的自然就是墙和家具的横切轮廓。

## 动机

里程碑 A（轨迹折线 + 方向三角）合进了 `7824659`，A 的定位是「先只画轨迹、数据全在手」。
B 才让小窗第一次有内容可言 —— 它是锚点标记、重定位「显示即验证」、路线回看三件事的载体。

**规划稿（`~/.claude/plans/2d-recursive-barto.md`）里 A 用的是逐帧自动 fit，用户否决了：**

> 我的想法是固定地图缩放比例，你可以按加减调整比例，画出地图可见的所有点云

否决的理由（用户的口径）：

| | 自动 fit | 固定比例 + 加减 |
|---|---|---|
| 画面 | 每帧自己在缩放/平移 ⟹ 看久了「飘」 | 只有你在动，比例**是你定的** |
| 离群点 | 远处一个坏三角化的点就把 bbox 撑爆 ⟹ 轨迹缩成一小团 | 撑不爆，画出框就裁掉 |
| 心智 | 「它为什么突然放大了」 | 我知道现在是 1:100 |

**顺带这是里程碑 A 的一处漏账**：`fit()` 没有任何离群点保护，会把沿途看过的远处点也圈进来
—— 那正是固定比例顺手解决掉的问题。

## 改动

**上游补丁 14 —— `thirdparty/orb_slam3/{include/System.h, src/System.cc}`**

- 新增 `GetAllMapPoints()`，转发 `mpAtlas->GetAllMapPoints()`。**我们这层不加锁**：
  只读 `mpAtlas`（构造时赋一次），锁在下面两层（`Atlas::mMutexAtlas` + `Map::mMutexMap`）。
- `thirdparty/README.md` 记第 14 条。

**C++ 我们这侧 —— `app/src/main/cpp/slam_engine.{h,cpp}`**

- `Engine` 加 `mapSnap` / `mapSnapMutex` / `mapBuild` / `mapSnapAtMs`(atomic) / `mapCloudOn`(atomic)。
- `rebuildMapSnap()`：枚举全图 → stride 抽稀 → 跳 `isBad()` → 取 xyz → 锁内和 `mapBuild` **对换**。
- `maybeRebuildMapSnap()`：1 s 闸门 + **队列空**才做。
- worker 循环两处调它：**超时分支** 和 **刚处理完一帧**。
- `getMapPoints()` / `setMapCloudEnabled()` 两个对外口子。
- `start()` 清 `mapSnap` + 闸门归零；`r.kfCount == 0` 的重置分支同样清 + 归零。

**JNI / Kotlin 声明** —— `jni_bridge.cpp`、`SlamBridge.kt` 各加两个，形状照
`nativeGetTrajectory`（出参）和 `nativeSetMeasuring`（开关）。

**`MapView.kt` —— 改动最大的一处**

- **删 `fit()`**（bbox + 自动缩放）⟹ 变换参数从 `(scale, cxWorld, cyWorld)` 换成
  `(pxPerMeter, cx, cy)`。`worldToView()` 仍是**唯一变换**，A 那条纪律没破。
- 缩放档位表（米/dp，相邻 ×1.5）+ `zoomIn()` / `zoomOut()`；中心跟着当前位置（没位姿时冻结）。
- `setSliceRange(m)`：切片厚度，由抽屉滑块推。
- 点云绘制：一遍 O(n)（切片 + 窗口双重过滤 → 转屏幕坐标 → 写 scratch）→ 一次 `drawPoints`。
- `Snapshot` 加 `pts / ptsN / curZ`；`pts` 只拷**用到的部分**（`copyOf(ptsN * 3)`）。

**`MainActivity.kt` / `activity_main.xml`**

- `mapWrap` 包住 MapView，右下角两个 28×30dp 的 `+` / `−`。
- 抽屉加两条：「小地图」`SwitchCompat`（**排在厚度上面**，它是父设置）+ 厚度滑块 + 当前值。
- `refreshMap()` 多读一次点云；**小地图关着时整个早退**（轨迹也不读）。
- `hint` 判据从「没有轨迹」改成「**两样都没有**」。

## 决策

### 一、⭐ 缩放按钮做成**真 `Button`**，不做画布上自绘的

A 里小窗**不接管触摸**（点它等于点预览，可以点画面中间那两个键之外的地方对焦）。
自绘按钮就必须让 `MapView` 吃掉**整个小窗**的触摸事件 ⟹ 那一条破掉。

真 `Button` 只消费自己那一小块，小窗其余部分照旧穿透 ✓ 代价只是一个 `FrameLayout` 包装。

### 二、⭐ 点云是**以当前高度为中心的浮动切片**，单色

```
zS += (zCam - zS) * 0.15                 // 低通
画:   |z - zS| <= range / 2
```

看到的自然就是**墙和家具的横切轮廓**（地板和天花板离你 1.5~3 m，被整层切掉）。
颜色是**单色**（浅蓝灰）—— 白给了轨迹、琥珀给了当前位置、青给了测量。

- **否决：按高度着色**（规划稿写的）。色相渐变的前提是每帧算 z 的 min/max，而**地图点一直在
  增加** ⟹ 只要来了一个更远的极值，整幅图的颜色就**整体跳一次**。那不是偶发，是每几秒一次。
- **否决：固定分区**（我上一版写的）。我当时的理由是「分区有界、浮窗会被手抖搅」——
  但**平滑过的中心一样有界**，而分区有个更糟的毛病：跨层那一下**整幅图一起换掉** ✗，
  浮窗只换边缘那几个点 ✓ 蹲下时是「一圈一圈地长出来」，不是「唰地换一张图」。
- **采用：浮窗 + 低通**。

⚠️ **低通不能在起步/重置/重定位时慢慢跟** —— 那三种情况下世界系整个换了，不特殊处理的话
切片会从老高度**一路滑过来**（1.6 s 的乱画）。所以 `|zCam - zS| > 1.5 m` 就**当场对齐**。
这条不是手感，是正确性。

### 三、⚠️ 切片厚度做成**抽屉里的滑块**，不是第三个按钮

用户提的（「把范围设置做成一个滑块，放到三横线里面」）。顺势立了一条分界：

> **设置放抽屉（持久化），视图状态放小窗（不持久化）**

厚度是调一次就不动的**设置**；比例是随时要拧的**视图**，所以留在小窗角上。
滑块 0.2~4.0 m，默认 1.0 m，和抽屉里另外两条一样记进 `SharedPreferences`。
滑块不可用时（小地图关着）跟着灰掉 —— 别让人去调一个看不见的东西。

### 四、⚠️ 上游补丁必须用 `Atlas::GetAllMapPoints()`，**不是** `GetCurrentMap()->GetAllMapPoints()`

规划稿 B1 写的是后者。`Atlas.cc:249` 那个 `GetCurrentMap()` 是：

```cpp
unique_lock<mutex> lock(mMutexAtlas);
if(!mpCurrentMap) CreateNewMap();
while(mpCurrentMap->IsBad()) usleep(3000);   // ← 锁是**抱着睡的**
```

`Atlas::GetAllMapPoints()`（`Atlas.cc:197`）自己锁 `mMutexAtlas` 后直接
`mpCurrentMap->GetAllMapPoints()` ⟹ **语义一样、不会挂**。

**`mpCurrentMap` 会不会是空**：`System.cc:170` 构造时就 `CreateNewMap()` ⟹ **从构造起非空**。
唯一的空窗在 `Tracking::Reset()` 里（`clearAtlas()` 和 `CreateNewMap()` 紧挨着），而它
**跑在 tracking 线程** —— 就是我们这个 worker ⟹ 对我们**不存在窗口，不需要判空**。

### 五、⭐ 快照在 worker 的**帧间空隙**重建，而且**「有帧等着就推迟」**

- 上游枚举是 `std::set` 的**整表拷贝**：节点各自分配 ⟹ 指针追逐 + 缓存 miss ✗；
  而且 `vector(first, last)` 对双向迭代器**先 `distance` 走一遍、再拷一遍** ⟹ **两趟** ✗。
  几万点就是**几毫秒**，不是零点几毫秒。
- 逐点只碰**抽中的**那些（`i += k`）⟹ 单点访问量（两次加锁 + 一次取坐标）与地图大小无关 ✓
- ⚠️ **那几毫秒抱住的是 `Map::mMutexMap`** ⟹ 挡的是 **LocalMapping**
  （`Map::AddMapPoint` 每建一个点都要拿它），**不挡 tracking**
  （tracking 用的是另一把 `mMutexMapUpdate`，`Tracking.cc:1895`）。

**⚠️ 光靠现成的 100ms 超时分支不够** —— 30fps 下帧一直有，`wait_for` 的谓词每次都立刻为真，
**超时分支根本不执行** ✗ ⟹ 必须在「处理完一帧、队列已空」那一处也调一次。

⚠️ 调用的位置有个坑：`if (e.frames.empty()) continue;` 在 `unique_lock qMutex` 的**作用域内**，
在那儿调 `maybeRebuildMapSnap` 会**死锁**（它自己也要拿 `qMutex`）。所以拆成
「出作用域后再调」。

### 六、20000 点封顶，**能装下就不抽稀**

用户的要求是「画出地图里可见的所有点云」。单房间的规模（几千~两万）**根本不该抽稀**；
超过 20000 才按 `k = ceil(n/20000)` 抽。

**持久缓冲对换**：`mapBuild` 建完和 `mapSnap` **swap** ⟹ 上一份回收成下一次的缓冲，
稳定之后**零分配**（否则每秒一次 240 KB 的分配/释放）。

### 七、⚠️ 小地图开关**必须连 C++ 一起停**（我一开始说不用停，是错的）

用户问「快照每次都要复制吧，开销不是很大吗，为什么不停，而且 SLAM 也要用这个吧」——
**三点全对，我原来的判断是错的**：

| 我以为 | 实际 |
|---|---|
| 0.5~3 ms/秒，可以忽略 | 红黑树指针追逐 + 两趟遍历 ⟹ **几毫秒/秒** ✗ |
| 只是一点 CPU | 那几毫秒**抱着 `mMutexMap`** ⟹ 挡 **LocalMapping** ✗ |
| 关掉只影响可见性 | ⟹ C++ 得加一个开关 |

藏起来时用户正在跑 SLAM，**正好是最不该白付这笔账的时候**。

### 八、⚠️ 轨迹那边：**记录停不了也不该停，读跟着一起停**

用户接着问「这个停的话轨迹是不是也可以停，要记录轨迹的话就最后访问一次记录」——
**后半句完全对**，前半句要分开看：

| | 谁在跑 | 停得掉吗 | 该停吗 |
|---|---|---|---|
| **记录**（`mlRelativeFramePoses` 那四张表） | **ORB-SLAM3 自己**，`Tracking::Track()` 里每帧 push | ✗ 要改上游 | ✗ **不该** —— `trajectory.txt` 就是拿它拼的 ✓ 每帧 28 字节，基本白送 |
| **读**（`getTrajectory()`） | 我们，`refreshMap()` 里 4 Hz | ✓ | ✓ **该停** |

⚠️ 读这条路和点云那条**坏处不一样**：

| | 抱的锁 | 挡谁 |
|---|---|---|
| 点云快照（1 Hz） | `mMutexMap` | **LocalMapping** |
| 轨迹读取（**4 Hz**） | `mMutexTraj`（补丁 12 那把） | **tracking** ✗ —— `Track()` 每帧都要拿它 push 四个值 |

四条 `std::list` 锁步走（节点各自分配、指针追逐），几万帧就是 1~2 ms ⟹ **真的会挡帧**。
而**导出根本不依赖每帧读** —— `dumpTrajectory` 本来就是停的时候**一次读完**的。

⟹ `refreshMap()` 那**一个早退同时覆盖两者**，不额外花成本。

### 九、`hint` 的判据从「没有轨迹」改成「**两样都没有**」

A 里 `n == 0` 就显示提示。现在有点云可画了 ⟹ 改成 `trajN == 0 && ptsN == 0`，
否则「点云出来了但被一句提示盖住」。

## 遗留

### ⚠️⚠️ 首次上机暴露的三条（用户反馈，下次做）

**甲、地图重置后轨迹没清 ✗ —— 这是上一批引进来的一处真 bug。**

设计上靠**跨图过滤**自动滤掉老帧（决策五那条），而那建立在
**「重置会换一张 `Map` 对象」**上（`Tracking::Reset()` → `clearAtlas()` + `CreateNewMap()`）。
真机上没清 ⟹ 说明走的是**另一条路**：`Tracking::ResetActiveMap()` → `mpAtlas->clearMap()`，
**原地清空同一张 Map** ⟹ 老帧的参考帧 `GetMap()` 还等于当前图 ⟹ **跨图判据根本看不见它**。

**修法（两条路都盖住）**：既然重置已经检测得到（`r.kfCount == 0` 那个分支），就在那儿
**显式**调 `sys->ClearFrameTrajectory()` —— 一次运行 = 一份轨迹，和 `start()` 同一个语义。
⚠️ 副作用：清掉的那段进不了 `trajectory.txt` 了 —— 但这就是想要的（重置后世界系变了，
两段本来也拼不起来）。

⚠️ **这行代码是上一批删掉的**：`2026-10-14-trajectory-follows-keyframes.md` 决策五写着
「重置之后老帧自动被滤掉 ⟹ 我们不用自己清轨迹」，然后删掉了 reset 分支里的 `traj.clear()`。
**那个「自动」只在换图那条路上成立** ✗ —— 记在这儿，免得下次又推一遍。

**乙、缩放能放大的还不够。** 档位表最小一档是 `0.02 m/dp`（140dp 小窗看到 2.8 m）。
要的是**再往里几档** + **按住连续缩放**（现在是点一下走一档）。顺带该有上下限，
到底了按钮就该灰掉而不是静默无事发生。

**丙、（未多次验证）「感觉重置次数变多了、初始化更难了」。** 只是感觉，没对比过。
下次量的时候看 `logcat` 里 `[M5] 地图被重置（第 N 次）` 的**时间分布**。
两个先验：这个项目**本来就是**「session 太短就初始化不了」（要 60 秒以上、前 15 秒持续平移），
所以「初始化难」可能是老现象；而这一批新加的锁占用（点云抱 `mMutexMap`、轨迹抱 `mMutexTraj`）
**理论上**只让 LocalMapping/tracking 慢几毫秒，不该改变重置的**次数** —— 但要量过才算数。

### 其余

- ⚠️ **可见时那个 4 Hz 的轨迹读取仍会挡 tracking**（1~2 ms，决策八）。要根治得让
  `getTrajectory` 不抱 `mMutexTraj` 走整张表（比如 1 s 快照一次 + 末端补当前点），**另一件事**。
- **可见时点云仍是 1 Hz**。若真机看出 LocalMapping 被拖（建图变慢、关键帧攒下来），
  旋钮是把它放到 2 s。
- **切片是在绘制时滤的，不是导出时滤的** ⟹ 地图超过 20000 点时切片拿到的是**抽稀过的** 1/k。
  室内规模根本不会超，所以现在没差。真跑大场景了再改成按 zS 在快照时就滤
  （代价：切片滞后 ≤1 s，而且要把 `range` 推给 C++）。
- 缩放**不持久化**（抽屉的设置持久化、小窗的视图状态不持久化）。只有加减，**没有捏合**。
- 点云**只滤 `isBad()`**，没做统计滤波 ⟹ 离群点会画出来（只是不再撑爆 bbox 了）。
- `mMutexAtlas` 可能在别人 `GetCurrentMap()` 的 usleep 里被持有 ⟹ 我们那次快照要等它几毫秒
  （不是每帧发生）。
- `Snapshot` 每拍拷全量点云（最多 240 KB）；真机上若 GC 显形，改成只拷窗口内的子集。
- **默认厚度 1.0 m 是拍的**（好在是个滑块）；低通那两个数（`0.15` / `1.5 m`）也是拍的。
- 切片中心跟着**手机的高度**走：举高手机看到的切片就高。要「固定切在离地 1.2 m」
  得另加一个基准（得知道地板在哪儿），**决定不做**。
