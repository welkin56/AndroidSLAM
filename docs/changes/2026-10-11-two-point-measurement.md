# 2026-10-11 阶段六 (b)：多点折线测距

一句话：**在测距开关下加一条多点折线** —— 十字对准目标按「加点」把当前读数钉成世界坐标，
点连成折线、每段标长度。**距离全部在 Kotlin 算，native 只多了一个投影函数。**

## 动机

单点尺度验收通过后，用户提出要做 (b)：

> 「测距两点距离的话，做这个能够验证单点距离远近吗」
> ……**「好了单点尺度验收通过，先做双点吧」**

并给了交互草案：

> 「**1 ui 怎么设计，2 支不支持多次测距显示在屏幕上**，即添加一个点，然后可以拉取到另一个点
> 然后一直拉取，直到点中断。中断后这些点保留，可以继续点击添加吸附到之前点或新点测距，
> 最后点重置清除所有点」

**「拉取」= 上一个点钉住不动，橡皮筋跟着十字拉，按一下定格。** 折线就是这个意思。

STAGE6 §2.3 早就写好了这个交互（`添加标记点` → `确定`），§2.4 甚至已经写了
`MeasureSession { points: List<Vector3f> }`。**这次是把它兑现。**

## 改动

- `cpp/measure_center.h` — 加 `initIntrinsics()` / `projectWorld()` 两个声明。
  **只用 float，不能出现 `cv::`/Eigen** —— `slam_engine.cpp` 会 include 这个头，而那个 target 刻意不链 OpenCV。
- `cpp/measure_center.cpp` — ① **平面兜底补上世界坐标**（见决策三）；
  ② 新增 `initIntrinsics()`（从 `Settings` 读 fx/fy/cx/cy）和 `projectWorld()`（世界 → 像素，纯手算矩阵）。
- `cpp/slam_engine.cpp` — `construct()` 里 `System` 造好之后调一次 `initIntrinsics()`；
  新增 `projectPoints()`（自己取 `e.pose`，调用方不用传位姿）。
- `cpp/slam_engine.h` — 声明 `projectPoints`。
- `cpp/jni_bridge.cpp` — `nativeProjectPoints(world, out)`。输入只读用 `JNI_ABORT`，输出写回。
- `java/.../SlamBridge.kt` — 声明同上，写清「只影响画，不影响距离」。
- `java/.../PreviewView.kt` — `Overlay` 加 `marks`/`segs`/`live`；
  **抽出 `toScreen()`**（原来那个变换内联在 `drawMeasure` 里）；画折线 / 点 / 段标签；
  `drawOutlinedText()` 把「黑描边 + 白填充」那两遍收成一处。
- `java/.../MainActivity.kt` — 会话列表 `pinned`、三个按钮、投影、**地图重置时清空**。
- `res/layout/activity_main.xml` — 预览和「结束/重定位」之间加一行 `[加点][撤销][重置]`，测距关时 `GONE`。

## 决策

### 一、会话放 **Kotlin**，不放 C++

**⭐ 关键：两点距离是 `‖pw_i − pw_j‖` —— 位姿根本不在里面。**
两点都在世界坐标系里，长度是它们的差。**相机在哪、朝哪，一点都不影响这个数。**

而单点距离是 `‖Tcw·pw‖`，位姿就在里面。**这是两者最本质的区别**（也是上一轮跟用户讨论清楚的那条）。

既然距离不需要位姿，C++ 就没有存会话的理由：

| | |
|---|---|
| 「加点」 | 把 `measureBuf[1..3]` 追加进列表 —— **零 native 调用** |
| 「撤销 / 重置」 | 纯 Kotlin |
| 「返回主界面时会话保留」 | 天然成立（STAGE6 §7）|
| **「要加哪个点」** | **不用新接口** —— 就是十字当前指的那个，`nativeGetMeasure` 每帧已经在回它的世界坐标 |

**代价**：多一个每帧 JNI 调用（投影）。但它**只在有已放点时发生**，而且只有几个点 ——
相比 `pollMeasure()` 里已经在调的 `nativeGetMeasure` / `nativeTrajSize` / `nativeResetCount`，量级可忽略。

> **📌 2026-10-12 追加：这一条被翻掉了一半。**
> 真机上发现点会漂（「本来在地板上，走一圈就飘到空中」）—— 根因是**坐标是快照，而 BA
> 一直在挪地图点**。修法是让点**认住 `MapPoint*`**，而那个只在 C++ 侧拿得到
> ⟹ **native 必须加东西，这条「一个字都不用加」的立论就不成立了**。
> 连链状态（`startsChain`/`closed`）也一并挪了过去，**Kotlin 只剩「照着缓冲画」**。
> 距离**也改成 C++ 算**（不用再把世界坐标喂回来）。见
> [2026-10-12](2026-10-12-pinned-points-follow-mappoints.md)。
>
> **只增不改** —— 上面那段原文留着，它是当时的真实推理。

### 二、⭐ 投影的内参从 `Settings` 的公开接口读，**不给上游打补丁**

STAGE6 §0 和 §4.1 都写着「(b) 需要先加 `System::GetK()`」—— **其实不用。**

`System` 确实不给 K（`Tracking::mK` 是 `protected`，Tracking.h:290），**但 `Settings` 的公开接口就给**：

```cpp
Settings s(settingsPath, ORB_SLAM3::System::IMU_MONOCULAR);  // 公开构造
GeometricCamera* cam = s.camera1();                          // 公开
// cam->getParameter(0..3) = fx, fy, cx, cy（顺序见 Tracking.cc:549-553）
```

**⟹ 零上游改动**，`thirdparty/README.md` 不加第 12 条。**唯一真相仍是 `phone.yaml`**，
不抄常量，换设备自动跟着走。

**代价**：多解析一次那个 yaml（启动时一次，毫秒级）。

> 📌 **这条是 [2026-10-10 那份](2026-10-10-support-ring-and-texture-density.md)「决策九」的收尾。**
> 那次刚把写死的 `kFx` 删掉，所以这次**不能**为了投影再抄一份 fx 到 Kotlin 或 C++ ——
> 那正是刚拆掉的东西。**两件事指向同一条纪律：内参只有 phone.yaml 一个来源。**

### 三、⭐ 平面兜底**现在能给世界坐标了 —— 而且不需要内参**

原来那儿写着（`measure_center.cpp`）：

> ⚠️ **不给世界坐标**：沿光轴只知道深度，要变成点得知道十字的归一化方向，**那要内参**。

**这句话不成立** —— 因为**十字恒等于主点**（`cx,cy = 320,240` = 画面中心，2026-10-10 核过）。
主点那条视线在相机坐标系里**恰好是 `(0,0,1)`**：

```cpp
const Eigen::Vector3f pw = Rcwᵀ · (0, 0, z) + cam;   // 一行，一个内参都不需要
```

**⟹ 解掉了 STAGE6 §0 说的那个 blocker。**

**为什么必须做**：不动它的话，「加点」只在**路径 1 命中**时才能成功 ——
而路径 2 是**路径 1 落空时的兜底**，恰恰是加点最需要的场合。
**不加的话「按了按钮却没反应」会经常发生**，那是最坏的手感。

**质量怎么标**：路径 2 本来就是 `kFair`，所以钉出来的点**天然继承「不太准」**，不用新机制。
UI 据此把它画成**空心圈**。

> ⚠️ 同一处耦合：这个技巧**依赖 `cx,cy == 画面中心`**，和 `centerPx()` 是同一个假设。
> 注释里互相指了。标定出非零畸变后两处要一起改。

### 四、⭐ 投影在跟踪**不是 OK** 时直接返回 0

写完之后复查发现的，不是设计时就想到的：

`savePose()` 只在 `r.valid`（跟踪 OK）时调，所以**跟踪一丢，`e.pose` 就是上一帧 OK 的旧值**，
而且会一直停在那儿。拿它投影 ⟹ 标记被画到错的地方，而且看起来像**「贴在屏幕上不动」**。
用户转手机时那个观感非常像 bug，但其实是「位姿没更新」。

**⟹ 在 `projectPoints()` 里加一道闸：`GetTrackingState() != OK` 就返回 0。**
和 `centerMeasure()` 开头那道闸同理 —— 不是 OK 就没什么可说的。

**副作用**：跟踪一丢，折线整条消失（而不是画在错的地方）。这是有意的，也和十字变成「等待跟踪…」一致。

### 五、吸到已有点：**按当帧投影的像素距离，阈值 20 px**

新点落在某个已有点投影的 20 px 内 ⟹ **直接复用那个点的世界坐标**（精确闭合，不是新建一个几乎重合的点）。

- **为什么用像素不用世界距离**：用户是按**屏幕上看到的**判断「是不是同一个角」的。
  世界距离阈值在不同景深下含义完全不同 —— 3 m 处 20 px 约 16 cm，30 cm 处不到 2 cm。
- **20 px 和 `kSnapRadiusPx` 同值纯属巧合**，是**另一个常数**（那个吸地图点，这个吸标记点）。注释里写清了。
- 复用已经要算的投影 ⟹ **零额外成本**。

### 六、UI **只加一行按钮、画面上只加两笔画**，预览一个字不动

用户明确说了 UI 后面要大改（「后续估计要大幅度改动优化 ui 的」）⟹ **这一版刻意不做**：
总长、任意两点、屏幕外的边缘指示、标签避让、`MapChanged()` 的时效性提示。

**预览的黑边也没动。** 用户看了截图后选的「先不动预览，只做按钮行」。
量过：预览区约 1080×2100，画面按 480:640 缩完只有 1080×1440 ⟹ **上下各剩约 330 px**。
两条去掉它的路（`minOf`→`maxOf` 裁剪 / 预览收成画面比例、空出的那块做段列表）都记在遗留里。

**唯一的结构改动**就是那一行按钮。⚠️ 预览是 `weight=1` ⟹ 这一行出现/消失时预览高度会变一次
—— 但那是**拨开关那一下**，不是每帧跳（被 `tvStatus` 折行坑过的那两次是后者）。

**标记点的颜色**：青色。白色是十字、琥珀是吸附圈、**青色是「我自己画的东西」**。

### 七、世界坐标系一变，会话**必须清空**

点存的是世界坐标。**地图重置会重新锚定坐标系** ⟹ 老点变成一张废图里的坐标，画出来是乱飘的。

`nativeResetCount()` 涨了 ⟹ 清空。用 `>` 而不是 `!=` —— `nativeStart()` 会把计数归零，那不算重置。

**⚠️ 但「拨测距开关」不清空** —— 会话保留，重开还在（STAGE6 §7 一致）。
唯一的手动清空是「重置」按钮。

## 验证

**1. 编译** ✓（本文件里所有的都过了）

```
> Task :app:assembleDebug
BUILD SUCCESSFUL
```

**2. ⚠️ 真机一行没跑。** 下面这些**全是推理，不是观察**：

- 折线画得对不对（尤其 `toScreen()` 那个变换 —— 见下）
- 平面兜底补出来的世界坐标准不准
- 吸到已有点的手感
- 地图重置时清空有没有生效

**⚠️ 最容易错的是 `toScreen()`。** 它原来内联在 `drawMeasure` 里只服务一个点，
现在抽出来服务所有标记和折线。**写错的话标记会和场景错位，而看起来像「SLAM 不准」。**
验的时候先单独验这一条（放一个点，人绕半圈看它跟不跟着场景走），再去看数字。

**3. 用户截图里的一个前置问题**

用户为回答 UI 问题给的截图里出现 **`地图已重置 20 次` / `22 次`**，而 `轨迹` 只有 14 / 0 点。
按「决策七」，那个频率下**会话会被反复清空**，这个功能根本没法验。
**做之前得先看这个**（大概率还是 STAGE5 那个惯性初始化问题）。

## 遗留

- ⚠️ **预览的黑边没动**（用户定）—— 两条路记在「决策六」
- ⚠️ **`kPointSnapPx = 20` 是拍的**，和 `kSnapRadiusPx` 同值纯属巧合，跑完看手感再定
- ⚠️ **投影和 `centerPx()` 同源耦合** —— 都假设 `cx,cy == 画面中心`
- ⚠️ **`Settings` 被解析了两遍**（System 一遍、`initIntrinsics` 一遍）。启动时一次、毫秒级，
  换来的是一条**更值钱的**纪律：内参只有一个来源。真要省，得等 `System` 暴露 K
- **屏幕外的点不画** —— 移出视野那段折线会消失（数字还在）。STAGE6 §2.6 要的边缘指示留到 UI 大改那轮
- **单向链，不能从中间插点** —— 只能追加 / 撤销末尾
- **标签会重叠** —— 点多的时候段标签可能压在一起
- **`MapChanged()` 的时效性提示**没做（STAGE6 §7）：回环优化后老点可能不再成立
- **段标签用了 `%.3f`（毫米）**，而单点读数是 `%.2f`（厘米）。**故意的** ——
  量的是物体尺寸而不是「到目标的距离」，毫米更有用。**但精度撑不住毫米，别当真。**
- **精度未验** —— 这是第一次拿两点距离对真值（A4 297 mm 最省事），**结果决定后面修哪儿**
