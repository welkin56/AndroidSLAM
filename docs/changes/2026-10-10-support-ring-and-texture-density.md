# 2026-10-10 支持度改成**多帧累积环** + 纹理密度（被一个 Eigen 的 UB 卡了三轮）

一句话：**支持度从「当帧匹配上的那几个点」改成「最近见过的地图点的累积环」，
环不去重（天然时间加权）；再加一条纹理密度。中途一个 Eigen 的悬垂表达式**让所有读数**静默消失**。**

## 动机

用户指出我把「支持度」实现错了：

> 「这个支持度当时我本来就是想要去**原图所有关键点**查找的……**我还以为你这个是多帧的**」

我原来做的是**单帧 + 只看匹配上地图点的那些** ⟹ 支持数就是「这一帧匹配了几个点」的镜像 ✗
同一张桌子这帧 4 个、下帧 1 个 → **门槛时过时不过** ✗

**⚠️「多帧」我试过一次，但做成了「去抖」**（最近 4 帧深度不稳就不采纳）——
那是**延迟**，丢失率 20%→39%，已撤。用户要的是**累积**，不是**去抖**。

## 决策

### 一、⚠️ **先纠正我自己一个错判**：不去重**不会**让支持数一直涨

我一开始反对用户提的「不去重」，理由是「相机不动时支持数会一直涨」。**错了** ——
**环是定长覆盖的**，填满就挤掉最旧的，所以**会饱和**。

**而且不去重的区分力强得多**（用户提的，理由也成立 ——
「很多帧都显示这里有点 ⟹ 可信度高」，**不去重就是天然的时间加权**）：

| | 好面（4 点） | 坏点（一闪而过） | 比值 |
|---|---|---|---|
| 去重 | 4 | 1 | 4 : 1 |
| **不去重** | 4 × ~50 帧 = **200** | 1 | **200 : 1** |

**实测印证**：有读数的支持度中位 **66**，测不到的**最大才 8** ✓

### 二、环存**世界坐标**，不存当帧的深度/角度

环里的点可能来自几十帧前。存「当帧的 z」的话相机一动就全过期。
**存 `pw`，每帧用当帧的 `Tcw` 现算** ✓ 而且**不加任何新锁** ✓

### 三、⭐ 卡了三轮的根因：`auto` + Eigen 的**悬垂表达式**

```cpp
auto pcOf = [&](const float pw[3]) {
    return (Tcw * Eigen::Vector3f(...).homogeneous()).head<3>();
};   //  ↑ 推出的是 Eigen::Block 表达式，不是 Vector3f
```

`Eigen::Vector3f(...)` 是临时对象，`.homogeneous()` / `Tcw *` / `.head<3>()` 一路都是
**引用它的表达式** —— 全在 `return` 时销毁，而 lambda **把这个表达式按值返回** ✗

**于是 `q.z()` 读到垃圾** ⟹ `q.z() <= kMinZ` 或角度判据随机成立 ⟹ 每个点都被 `continue` ⟹
`bestMp == nullptr` ⟹ **`支持` 恒为 0** ⟹ **一个读数都出不来** ✓

**⚠️ 它是 UB：不崩、不报错，而且症状和「参数没调对」一模一样** ✗
**我因此白改了两轮常量**（0.02→0.024 / 0.04→0.047），**都没用**。

**修法**：显式写返回类型 `-> Eigen::Vector3f` ✓

> **详细写进了 [bugs/eigen-auto-dangling-expression.md](../bugs/eigen-auto-dangling-expression.md)** ——
> 这是那个目录要收的东西（坑的通用形状），不是本次事件。
>
> ⚠️ **顺带解释了一个怪现象**：环**之前**那版能出数，是因为它的 anchor 来自
> `Candidate::pc`（一个正经的 `Eigen::Vector3f`）—— **没有 `pcOf`** ✓

### 四、⚠️ 同一个常量在两处差 1.47 倍（自相矛盾）

```cpp
kSupportConeFrac = 0.047
  入环筛用**像素**：0.047 × w(640)    = 30 px   ✓
  查询筛用**角度**：0.047 rad × fx(435) = 20.5 px ✗   ← 同一常量，差 1.47 倍
```

**这不是「参数没调够」，是换算写错了** —— 放大数值只是两边一起放大，矛盾还在。

**修法**：角度那两个**单独定义、用真实 `fx` 换算** ✓

### 五、⚠️ 锚点**改回「当帧候选」**（从环里改回来）

修完 UB 之后出数了，但真机上用户报「**有些点本来应该可以吸上，但它没有**」✗
而日志显示：`测不到` 时 `支持` **恒为 0**，**包括 `候选11` 的那些行** ✗

**⟹ 逻辑上 `countSupport` 至少该数到 anchor 自己（θ 差 0、深度差 0）** ⟹
**`支持0` 只能是「根本没数」= 锚点没选出来** ✓

**根因**：锚点当时是**从环里按角度选**（15 px），**而环里的点没有当帧像素位置** ✗
**角度阈比入环阈（30 px）窄一半** ⟹「30 px 内有点、15 px 内没有」**一个都选不出** ✗

**修法**：**锚点从当帧候选里按像素距离选**（候选有真实像素位置，比角度准）✓
**支持度仍然从环里数** ✓ —— **两者数据源分开，各取所长** ✓

### 六、锚点做成**两级**（用户要求「吸附半径调小一点」）

| | 半径 | 后果 |
|---|---|---|
| **优先** | **20 px** | 「正好指着」，横向偏移小 ✓ |
| **兜底** | 30 px（整个入环锥） | 退到远处才找到 ⟹ **质量降一档** ✓ |

**为什么不能只调小**：20 px 内恰好没图点时，**一个数都不会有** ✗（就是上面那个问题）✗
**⟹ 宁可给一个不太准的数，也别「明明指着有东西的地方却什么都没有」** ✓

### 七、状态栏：**只加 `纹理`，不加距离**

用户报的现象：「**有测距数据时文字部分显示距离，会把预览部分挤下去一点，
没有测距时预览又回来**」—— 预览**上下跳** ✗

**根因**：`tvStatus` 是 `wrap_content` —— **多一行 / 折了行它就变高** ⟹ 把预览挤下去 ✗
（**不是** `PreviewView` 里画的十字 —— 那个画在画布上，不影响布局 ✓）

**⚠️ 我在这上面判断错了一次，而且是同一个错误犯了两次：**

1. **第一次**：我**新开了一行**放距离 ⟹ 直接多一行 ⟹ 挤 ✗
2. **改成并进「轨迹」那行之后**，我以为「变长不挤、只有换行才挤」✓
   —— **结果它真的折行了** ✗（`轨迹 1305 点　⚠️ 地图已重置 3 次　距离 1.620 m　纹理 14` 太长）
   ⟹ **用户实测「还是会挤下去」** ✓ **我的那句判断被自己推翻。**

**最终做法（用户定的）**：**只加 `纹理`，不加距离** ✓
- 距离**十字旁边本来就有** ✓ ⟹ 状态栏那份是重复的 ✓
- 去掉之后那行短了一半，不折行了 ✓

**顺便**：`纹理` 原本**传到了 Kotlin 但没人用** ✗ 现在有消费者了 ✓
而且它**在没读数时也有值** ✓ ⟹ **正好告诉用户「这地方为什么测不了」** ✓

> **教训**：`wrap_content` 的 TextView，**一行之内的长度变化不挤，但一旦折行就挤** ✗
> 判断「会不会折行」得看**最坏情况有多长**，不能只看典型值 ✗

### 八、心跳：**改成「只在测不到时打」**

原来那个「不管有没有读数都每 2 秒打一行」是**临时调试**用的 ✗ 用户要求清掉 ✗
**但全删的话，「一直测不到」在日志里又是空白** ✗ —— 而那**恰恰是这个项目最常见的问题** ✗

**⟹ 改成**：只在 `quality == kNone` 时每 5 秒打一行 ✓
有读数走原来那条（只在变化时打）⟹ **正常使用时不会刷屏** ✓

### 九、⚠️ 后续：**把两处 `/ kFx` 写成直接弧度，删掉 `kFx`**

📌 **这是对「决策四」那个修法的收尾，不是改判** —— 决策四的结论（**不能拿 `w` 顶替 `fx`**）仍然成立且更值钱。

**起因**：用户连问了四轮「为什么要有像素→角度的换算」。

他的推理是：**判断「还指着吗」只需要当前位姿 + 世界坐标** —— **他完全对** ✓
`axisAngle(Tcw · pw)` 就是纯几何，**运行时不碰内参**。

**那 `45 / kFx` 是什么**：它**不是每个点的换算**，是**一个数字的单位标注**（编译期一次）。
等价于：

```cpp
constexpr float kSupportConeRad = 30.0f / kFx;   // ← 换掉
constexpr float kSupportConeRad = 0.0689f;       // ← 就这样，程序一样
```

**唯一的作用是让「30 px」这个数只有一份**，好和另外两处按像素定的锥（`kSnapRadiusPx = 20`、入环筛 `0.047·w`）对齐。

**为什么还是删了** —— 这个「记账」的**收益抵不上四次困惑**：

| | 换成直接写弧度 |
|---|---|
| ✅ 换来 | 代码直白，不用在脑子里做单位换算 |
| ❌ 失掉 | **换设备的自动缩放** —— `fx` 变 800 时 `30/800` 会自动变成新机上的 30 px；写死就变成 55 px（**不报错，只是锥悄悄变宽**）|
| ❌ 失掉 | 一眼看不出三根锥是同一套单位 |

**⟹ 权衡**：`kFx` 本来就是**写死的**，没人帮你查设备 ✓ 那个「自动缩放」在换机前**是假的** ✗
**而看不懂是真的、现在就在付的** ✓ **⟹ 删。**

**改法**：两个常量直接写弧度（`30/435.2 = 0.0689`），**把来源和换算方式写进注释**
（`fx = 435.2`、`30 px → 0.0689 rad`、⚠️ 不能除 `w`）——
**信息一条不少，换算不做了** ✓

**行为完全没变**：`0.4 × 0.0689 = 0.02756`，和原来 `0.4 × (30/435.2)` 一模一样 ✓

> **教训**：**「让人看懂」是硬指标，「记账方便」是软指标** ✓
> 我连着四次把软指标排在硬指标前面 ✗ **用户第四次问，就是该改的信号** ✓
