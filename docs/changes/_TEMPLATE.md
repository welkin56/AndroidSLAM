# YYYY-MM-DD 一句话说清这次改了什么

> **这是一张空白表格，不是一份记录。** 它的作用只是让每份记录长得一样，
> 审查的时候知道「决策」永远在哪一节，不用每次重新找。
>
> 用法：复制本文件 → 改名成 `YYYY-MM-DD-<english-kebab-slug>.md` → 填。
>
> ```bash
> cd docs/changes
> cp _TEMPLATE.md 2026-09-20-some-change.md
> ```
>
> 文件名前面的下划线让它排在目录最前，也提醒「这个不是记录」。

六节都要有。某节确实为空就写「无」——**空着和漏掉是两回事**，
审查的人看到「无」才知道是想过了，看到缺失只会以为是忘了。

## 动机

用户提了什么需求，或者出现了什么现象。**带上触发它的那条消息 / 那段日志。**

如果是 bug：症状是什么，什么条件下出现，怎么发现的。

## 改动

按文件列。每条写**改动的意图**，不是 diff 的复述 —— diff 自己能说明「改了哪几行」，
说不清的是「为什么要这么改」。

- `path/to/file.ext` — 做了什么，为什么。

## 决策

**这一节是整份记录的核心价值所在。** git 只记录存活下来的那个版本，
记不下别的路；而恰恰是那些没走通的路最费时间。

考虑过但否决的方案，逐条写：方案是什么、为什么否决。

- **否决：** 方案 X。理由：……
- **采用：** 方案 Y。理由：……

如果过程中用户纠正了我的判断，也写在这里 —— 那通常意味着我的默认想法是错的，
不写下来下次还会错一遍。

## 验证

跑过的命令 + **实际观察到的**结果。贴真实输出。

```
$ 命令
输出……
```

**没验证的就写「未验证」**，不要含糊过去。这一节的要求比看起来重要：
这个项目的坑几乎全在「看起来应该对」的地方。

## 遗留

已知没做的、已知的坑、暂时绕过的。要说清是「暂时绕过」还是「决定不做」。

## 回滚

怎么撤销这次改动。文件级的写清楚改回什么；涉及多处的给顺序。
