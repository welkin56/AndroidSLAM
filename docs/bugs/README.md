# 踩过的坑

**这里和 [`changes/`](../changes/) 分工不同：**

| | 记什么 | 怎么找 |
|---|---|---|
| `changes/` | **按时间**：这一次改了什么、为什么这么改 | 按日期 |
| **`bugs/`（这里）** | **按坑**：这类问题长什么样、怎么认出来、根因是什么 | 按名字 |

改动记录是给「审查这次改动」看的；这里的东西是给**「又撞上一个怪现象」**的时候翻的 ——
一份一条，标题就是那个坑。

---

## 目录

| 坑 | 一句话 | 发现 |
|---|---|---|
| [线程栈太小](thread-stack-too-small.md) | Android 的 pthread 默认 **1 MB** 栈，而 PC 主线程是 8 MB —— 深度 C++ 调用链在 PC 上没事、在安卓上 `SIGSEGV` | 2026-09-28 |
| [静态库被链进多个 .so](duplicated-static-lib-symbols.md) | 同一个 `.a` 被链进两个 `.so`，进程里就有**两份**它的全局状态（`parallel_for_` 背后的 TBB 并行引擎就这么炸的） | 2026-09-28 |

> ⚠️ **这两条是同一次崩溃的两个原因，而且缺一不可。**
> 「修了 A 之后还坏」**只能说明 A 不充分，不能说明 A 不必要** ——
> 要判断必要性，得在其他变量都干净的前提下单独摘掉它试。

## 共同的教训：**tombstone 只有 1 帧栈**

这两条都是从「`SIGSEGV` 但 tombstone **只有 1 帧栈**」这个形状里挖出来的。
那种 tombstone 几乎没用：

- 符号化会落在 **STL 内部**（被链接器的同形函数合并误导，指到一个根本不会执行的函数）
- 栈展开器在第一帧就放弃

**出路是自己展开。** 可复用的崩溃处理器代码在
[changes/2026-09-28-m5-slam-on-phone.md](../changes/2026-09-28-m5-slam-on-phone.md) §6 的附录里 ——
它给出 `xxx.so+0x偏移`，配合未 strip 的 `.so` 用 `llvm-addr2line` 反查。
**那一次就是靠它 14 帧栈一路指到根因的。**
